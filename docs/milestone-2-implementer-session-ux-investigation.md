## 1. Executive conclusion

## 2. Current trusted Implementer path

## 3. Root-session visibility

**Creation and history.** Public `session.create` passes `title`, `agent`, `model`, `location`, and permissions to core `Session.create`, which publishes `SessionEvent.Created` and persists a `Session.Info`. Omitted `parentID` makes this a root. The returned ID and record exist before the create request resolves; there can be a short client/event synchronization delay before every UI cache reflects it. Core session listing can filter `parentID: null`, and the normal TUI session picker explicitly requests that filter and excludes children from its options. Thus the plugin-created Implementer is eligible for the ordinary root-session list as soon as its create completes, while the exact paint timing is not guaranteed by source. Manual root creation and plugin root creation converge on the same server session record and route renderer; no origin-specific rendering branch was found. [Host: `../opencode/packages/server/src/handlers/session.ts:session.create` lines 124–140; `../opencode/packages/core/src/session.ts:Session.create` lines 250–286; `../opencode/packages/core/src/session/store.ts:SessionStore.list` lines 99–138; `../opencode/packages/tui/src/component/dialog-session-list.tsx:DialogSessionList` lines 63–76, 142–190.]

**Identity and status.** `Session.Info` stores ID, optional `parentID`, agent, model, title, outcome, location, and timestamps. The session picker shows title (or fallback), date grouping, and a running spinner; it does **not** display all of agent/model/status as separate picker columns. Those data are available through the public session/data APIs, and the normal transcript's assistant footer labels the actual agent and model after assistant output begins. Session tabs, when enabled, report `busy`, attention, and unread state. A deliberately distinct M2 title plus the stored exact ID identify the Implementer; its configured role agent and model should be verified from the created session as part of M2 planning. [Host: `../opencode/packages/schema/src/session.ts:Info` lines 30–59; `../opencode/packages/tui/src/component/dialog-session-list.tsx:DialogSessionList` lines 153–190; `../opencode/packages/tui/src/routes/session/index.tsx:AssistantFooter` lines 1865–1903; `../opencode/packages/plugin/src/tui/context.ts:UI.tabs` lines 481–501.]

**Transcript.** A session route syncs the requested session and its messages, then renders the ordinary session rows. Assistant parts include text, reasoning, and tools; the footer shows agent/model. Reasoning appears only when a model/host emits exposed reasoning; OpenCode's default `hide` mode collapses it to a clickable summary, and its thinking toggle can change that. Tool inputs, progress, and results render as normal tool rows; final text stays in the same transcript. The session and projected messages remain available through `session.get`/message listing after execution reaches an idle outcome, subject to normal retention, deletion, and history pagination. None of these mechanisms checks `parentID`. `parentID` is used for family grouping and native child navigation, not ordinary transcript rendering. [Host: `../opencode/packages/tui/src/routes/session/index.tsx:Session` lines 166–168, 328–349, 1387–1425; `:SessionPartView,:AssistantFooter,:ToolPart` lines 1827–1903, 2392–2450; `../opencode/packages/tui/src/routes/session/message-parts.tsx:ReasoningPart` lines 42–117; `../opencode/packages/client/src/solid/data.ts:session.message.sync` lines 1614–1645.]

The root Implementer will **not** appear in the Orchestrator's family picker or as a clickable `subagent` tool row in its transcript. Those affordances depend on `parentID` or on a native tool part with child metadata. They are nice-to-have structural features, not prerequisites for the separate root's normal transcript. [Host: `../opencode/packages/tui/src/util/session.ts:sessionFamily`; `../opencode/packages/tui/src/routes/session/index.tsx:Subagent` lines 3106–3138; `../opencode/packages/tui/src/routes/session/composer/subagents-tab.tsx:SubagentsTab` lines 36–59.]

## 5. While-running observability

`session.prompt` is an **admission** API, not a request that waits for the assistant's final response. Its input is prepared and admitted to the durable inbox, `execution.wake(sessionID)` schedules execution, and the endpoint returns the admitted user item/ID. The public client has no separate `promptAsync` operation because this prompt operation already returns before completion; `session.wait` is the distinct operation that blocks until the session is idle. M1 explicitly awaits prompt, then awaits wait. The Implementer can therefore be routed before prompt submission (after create and identity/freshness checks) or immediately after the prompt returns. Routing before prompt gives the UI time to mount and subscribe before work starts; routing after prompt avoids displaying an unprompted session during an admission failure. Neither ordering changes the ID used by M1 for result checks. [Host: `../opencode/packages/core/src/session/session.ts:Session.prompt` lines 145–179; `../opencode/packages/server/src/handlers/session.ts:session.prompt,:session.wait` lines 305–330, 449–454; `../opencode/packages/client/src/effect/api/api.ts:SessionPromptInput/Output,:SessionWaitInput/Output` lines 267–279, 331–333; project: `src/m1/attempt.ts:runM1` lines 177–194.]

The TUI client receives server events independently of the plugin's pending wait and updates per-session state: execution started/succeeded/failed, user admission, text deltas, reasoning deltas, tool input/call/progress/result. The session route reads those reactive messages, so source supports a live normal transcript for the Implementer root as it runs. The session-list picker also marks a running root with a spinner. The session view can sync an arbitrary selected session by ID; prompt and result operations continue to address the stored ID even if the operator changes routes. [Host: `../opencode/packages/tui/src/context/client.tsx:onEvent` lines 20–58; `../opencode/packages/client/src/solid/data.ts:handleEvent` lines 631–641, 773–789, 838–1002, 1009–1062; `../opencode/packages/tui/src/routes/session/index.tsx` lines 166–168, 328–349, 1417–1425; `../opencode/packages/tui/src/component/dialog-session-list.tsx` lines 173–179.]

**Interactive limit:** source shows plugin keymap commands may return `Promise<void>` and the route/event layers are independent. It does not itself prove that all keyboard navigation, dialogs, scroll updates, and the completion toast remain comfortable during a real Implementer run while the launch command awaits `session.wait`. The existing M1 live dogfood did not record this. Do not upgrade this inference to a runtime claim. [Host: `../opencode/packages/plugin/src/tui/context.ts:KeymapCommand.run` lines 384–410; `../opencode/packages/tui/src/context/keymap.tsx:createLayer` lines 205–266; project: `docs/milestone-1-live-dogfood.md` lines 16–23.]

## 8. Remaining runtime uncertainty

**One bounded navigation dogfood is still necessary to confirm interactive quality, not to establish an API seam.** In a disposable/clean worktree under the established M1 safeguards, run one small authorized Implementer attempt using the current installed OpenCode version and an instrumented *future* M2 navigation sequence: record the Orchestrator ID; CAP-create a fresh Implementer root; route to it before or just after prompt admission; keep the trusted wait/Git check; watch at least one ordinary tool row and any exposed text/reasoning; use `/sessions` or tabs to switch to Orchestrator and back while work is active; verify the completion PASS/STOP toast's Open action and the finished transcript. Confirm no keyboard/dialog focus trap, no lost event projection, and no misbound result if the visible route changes. If auto-focus is awkward, repeat only the navigation portion with the picker-first flow, not a second implementation run. This is a proposed future probe, **not performed in this investigation**. The current task and repository guidance prohibit running OpenCode for this static investigation. ## 9. Recommendation

Proceed to **one bounded navigation dogfood**, then M2 implementation planning if the observed interaction matches the source-established route/event behavior. Plan the simplest flow around `ui.router.navigate` to the exact CAP-created Implementer root, normal session transcript, native `/sessions`/tabs for navigation, and an informational toast linked to the stored Orchestrator ID for completion. No in-repo navigation bridge is required at present; a one-command or session-linked-toast “View Implementer” affordance remains a tiny navigation-only fallback if dogfood reveals a usability gap. Preserve the M1 admission and Git gates exactly, and stop after the scope check. Do not pursue an OpenCode `parentID` API change for this M2 UX.
