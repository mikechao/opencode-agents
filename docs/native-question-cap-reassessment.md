# Native Form/Question as CAP authorization: threat-model reassessment

Investigation only, 2026-09-28. This report assesses the authorization interaction alone. It does not change the accepted M2 native-child decision or propose an implementation.

## Baseline and decision rule

The checkout is `50babfeca3169661bc4b372679423c75b1420770` with a clean worktree before this report. The root declares `@opencode/plugin` `2.0.17`; installed `@opencode/plugin` and `@opencode/client` are `2.0.17` ([root package](../package.json), [installed plugin](../node_modules/@opencode/plugin/package.json), [installed client](../node_modules/@opencode/client/package.json)). The installed CLI reports `opencode v2.0.18` (read-only `opencode --version`, with its log directory redirected outside the worktree), and the read-only sibling host checkout is `v2.0.18`. The plugin declarations and host source therefore differ by one patch version; the relevant form client methods exist in the installed `2.0.17` declarations, and their server behavior below is from the `2.0.18` host source. No live authorization form was opened or answered in this investigation.

The accepted rule is narrower than “no local client can synthesize a response.” V1 trusts the installed host/TUI, installed CAP plugin, permission enforcement, and local OS/user account; it does not demand physical-human attestation or defend against a trusted local client, same-user TCB modification, or OS-level input injection ([CAP §3](coding-authority-protocol.md#3-trust-boundary), lines 110–142; [charter](charter.md), lines 80–111). A local human/trusted client may manually re-prompt an editing-capable Implementer outside CAP without resurrecting a grant ([CAP](coding-authority-protocol.md), lines 73–85; [accepted M2 reassessment](milestone-2-native-child-threat-model-reassessment.md), lines 9–17, 48–52). But **model output and model-controlled actions must not become the affirmative result that creates a new CAP grant**: the trusted plugin must receive an affirmative trusted-UI result for its exact frozen candidate, then check liveness, binding, and freshness ([CAP](coding-authority-protocol.md), lines 44–71, 129–142). This is the criterion used here.

The [authorized Implementer](../.opencode/agents/authorized_implementer.md) allows `shell:*` except `git commit`; its instruction not to control sessions is behavioral, not a permission denial. The host shell tool checks the allowed command, then runs the process ([host shell tool](../../opencode/packages/core/src/tool/plugin/shell.ts), lines 116–151). The accepted M2 reassessment explicitly recognizes local client/HTTP and background-process routes from an ordinary Implementer shell, while declining to treat later ordinary session activity as surviving CAP authority ([reassessment](milestone-2-native-child-threat-model-reassessment.md), lines 42–52). This report does not reopen that decision. **A forged Form answer would differ:** trusted CAP code would consume it as a fresh authorization, rather than merely observing an ordinary later session prompt.

## The OpenCode 2.0.18 Form/Question path

`Form.Service.create` stores a pending in-memory form with a generated or supplied `frm_...` ID, session ID, title, metadata, and fields, then publishes `form.created`. `Form.Service.ask` simply calls `create` and awaits that form's deferred result; interruption cancels it. `Form.Service.reply` accepts any valid answer to a pending ID, publishes `form.replied`, stores `answered`, and resolves that same deferred. It checks pending state and answer shape, **not caller origin** ([core Form service](../../opencode/packages/core/src/form.ts), lines 120–203; [form schema](../../opencode/packages/schema/src/form.ts), lines 8–12, 122–173). The model-facing `question` tool checks `question` permission and calls this same `ask`; its answer is returned to the model, not to a trusted CAP authorization channel ([question tool](../../opencode/packages/core/src/tool/plugin/question.ts), lines 48–106). Neither `ask` nor the question tool adds a TUI-local or user-origin property.

Pending IDs are **enumerable**, not secret capabilities. `GET /api/form` returns all pending forms for the requested location, including their IDs, session IDs, fields, and options; its optional `location[directory]` query selects the worktree instead of the server's default directory ([global Form route](../../opencode/packages/protocol/src/groups/form.ts), lines 7–25; [global handler](../../opencode/packages/server/src/handlers/form.ts), lines 7–14; [location resolver](../../opencode/packages/server/src/location.ts), lines 39–46). `GET /api/session/:sessionID/form` does the same for a known session; its middleware resolves the session's location ([session routes](../../opencode/packages/protocol/src/groups/session.ts), lines 794–853; [form location middleware](../../opencode/packages/server/src/middleware/form-location.ts), lines 24–37). `POST /api/session/:sessionID/form/:formID/reply` takes `{answer}`. Its handler checks only that the form belongs to that session, then calls `Form.Service.reply`; no agent permission or TUI-origin check appears there ([session handler](../../opencode/packages/server/src/handlers/session.ts), lines 38–43, 637–689). The normal TUI form UI submits through this same `data.session.form.reply` path ([TUI form](../../opencode/packages/tui/src/routes/session/form.tsx), lines 269–272). The installed `2.0.17` public client declares `session.form.list/create/get/reply/cancel` and global `form.list` ([client declarations](../node_modules/@opencode/client/dist/promise/generated/client.d.ts), lines 83–89, 149–150); these are public client/server APIs, not internal-only Form methods.

The server requires a password and binds localhost by default ([server process](../../opencode/packages/server/src/process.ts), lines 46–57; [auth middleware](../../opencode/packages/server/src/middleware/authorization.ts), lines 72–94). That protects against an unauthenticated remote caller, but it does not distinguish a TUI gesture from an allowed same-user shell process. In the default managed-service topology used by the ordinary CLI/TUI, `opencode api` resolves the managed endpoint, adds its auth headers, and sends arbitrary method/path requests with a JSON body ([CLI API handler](../../opencode/packages/cli/src/commands/handlers/api.ts), lines 18–51, 64–77; [server resolution](../../opencode/packages/cli/src/services/server-connection.ts), lines 21–51, 74–83; [TUI default resolution](../../opencode/packages/cli/src/commands/handlers/default.ts), lines 31–47). Its public command accepts `method path` and `--data` ([CLI command schema](../../opencode/packages/cli/src/commands/commands.ts), lines 99–115). A shell-capable Implementer can therefore use `opencode api` to GET `/api/form` with the worktree location query, read the form's `id`, `sessionID`, and fixed choice value, then POST `/api/session/<sessionID>/form/<formID>/reply` with `{ "answer": { "<field>": "Authorize" } }` (for a required fixed-choice string field). This is a supported CLI route; no credential extraction or private core import is needed. The service credential is also stored for same-user reconnects and exposed by `opencode service get password` ([service config](../../opencode/packages/cli/src/services/service-config.ts), lines 127–163; [service get](../../opencode/packages/cli/src/commands/handlers/service/get.ts), lines 7–13).

Role permission enforcement applies to the Implementer's **shell tool invocation**, which its role permits. The HTTP handler does not recheck the initiating agent or its `question`/`shell` rules. Form ownership, answer validation, an exact candidate digest in metadata, and single-use settlement can bind an answer to a particular pending form; none proves that actor 1–3 rather than actor 6 supplied it. Freshness and generation checks would reject stale or changed candidates but would not reject an on-time synthetic `Authorize` answer. A prior authorized model could exercise its allowed ordinary shell during a pending form, or use the accepted background-process capability to watch for a later form ([reassessment](milestone-2-native-child-threat-model-reassessment.md), line 46). This is a reachable capability path shown by source, not a claim that such an attack was observed live. A separately isolated `--standalone`/remote server might change credential reachability; those variants are not the default supported local topology and do not remove this default path.

## `Form.Service.ask`, public plugin reachability, and Confirm comparison

The installed TUI plugin surface exposes form list/sync/reply/cancel and a full `OpenCodeClient`, but no direct `Form.Service.ask` hook ([TUI plugin declarations](../node_modules/@opencode/plugin/dist/tui/context.d.ts), lines 63–71, 458–464). `Form.Service.ask` is an internal server-core service, not a public TUI plugin API; importing or bridging it into the TUI would couple to internal host code and, more importantly, would still await the same publicly replyable Form. The native `question` tool is model-facing, denied to the present narrow roles, and must not be promoted into CAP authorization. There is no stronger Question route in the inspected 2.0.18 path.

By comparison, public `ui.dialog.confirm` creates a **TUI-process lexical promise**. Its `true` comes from the dialog's Confirm callback; Cancel returns `false`, and close/dismissal returns `undefined` ([TUI dialog API](../../opencode/packages/tui/src/plugin/api.tsx), lines 290–337; [Confirm widget](../../opencode/packages/tui/src/ui/dialog-confirm.tsx), lines 20–91). No session/client/server reply endpoint addresses that promise. A model can trigger trusted code to *open* the dialog but cannot use its permitted model tools or ordinary OpenCode HTTP client to resolve that exact pending promise affirmatively. The accepted M0 checks found no supported model/session/non-interactive positive-resolution route for Confirm ([CAP §12](coding-authority-protocol.md#12-relationship-to-milestone-0), lines 474–491). Synthetic OS input or code inside the trusted TUI could operate the widget, but those are expressly outside V1's guarantee. A Form instead deliberately exposes its affirmative settlement through a server API reachable from actor 6's allowed shell.

The earlier [native DX investigation](native-dx-ux-investigation.md) was too broad where it treated *any* programmatic client reply as dispositive. Under V1, actor 3's programmatic reply is allowed as trusted local action. Its rejection of Form nevertheless stands for a narrower, in-scope reason: actor 6 can programmatically manufacture the affirmative reply that trusted CAP code would turn into a fresh grant. This conclusion does not require a live probe; the installed public client declaration, 2.0.18 routes/handlers, default authenticated CLI path, and current shell permission establish the route. No probe should send an authorization reply to a real session.
