## 2. Selected UX and non-negotiable boundary

The [selected hybrid UX](hybrid-authorization-ux-decision.md) is the exact frozen plan in the **existing root conversation**, plus a compact `session.composer.top` strip with direct TUI-local Authorize and Cancel callbacks. Native Form/Question is already excluded; this report does not revisit it. The prior [DX](native-dx-ux-investigation.md), [Question](native-question-cap-reassessment.md), and [non-modal](native-nonmodal-authorization-investigation.md) investigations explain the existing decisions.

**Conversation is presentation, not CAP authority.** The trusted active plugin retains the frozen candidate and encoding/digest, canonical root and HEAD, parent/child/session bindings, freshness checks, local decision, and one-use grant ([CAP protocol](coding-authority-protocol.md)). Text resembling a plan, even an assistant message, has no authorization effect. The required extra property is that trusted code can prove the currently offered local decision corresponds to the exact candidate actually projected for the user to inspect.

## 4. `session.import` production reassessment

**Exact semantics.** The public experimental route takes the complete transfer shape (`info`, `messages`, optional target location), with no target session parameter ([protocol, lines 240–267](../../opencode/packages/protocol/src/groups/session.ts)). `SessionTransfer.import` sets `sessionID = input.data.info.id`, queries `session_v2`, and raises `ImportConflictError` if that ID already exists ([transfer, lines 64–73](../../opencode/packages/core/src/session/transfer.ts)); the server returns HTTP 409 ([handler, lines 143–160](../../opencode/packages/server/src/handlers/session.ts)). It therefore neither appends, merges, replaces, nor rewrites a live root. It creates another session under the supplied unused ID; it does **not** assign a new one for the caller.

Import accepts typed transfer metadata and messages. It preserves caller message IDs, roles/types, content/tool parts, timestamps, agent/model fields, and message metadata for *settled* messages, assigning fresh per-session sequence numbers. It filters incomplete assistant steps and running shell/compaction messages. The transfer schema includes user, assistant, synthetic, system, skill, tool-containing assistant, control, and idle messages ([message schema](../../opencode/packages/schema/src/session-message.ts), [transfer filter, lines 165–169](../../opencode/packages/core/src/session/transfer.ts)). `export` returns `sessions.get` plus ascending settled projected messages; it is not an atomic live-history rewrite transaction ([transfer, lines 57–63](../../opencode/packages/core/src/session/transfer.ts)). Pending inbox items, live execution claims, forms, and child session objects are not transfer messages. The import's `session.created` event uses supplied parent ID, title, agent/model, metadata and permissions, but resolves the target project/location and generates a new slug/version. It then sets cost/tokens and created/idle/viewed/archived times and outcome where idle is supplied. Not every `Session.Info` field is faithfully restored: for example, `fork` and `revert` are not copied in this path ([transfer, lines 89–143](../../opencode/packages/core/src/session/transfer.ts), [session schema](../../opencode/packages/schema/src/session.ts)).

The supplied `parentID` is checked for an existing parent and stored; it does not copy, reparent, or reconstruct the existing root's children. Tool parts with child IDs are message data, not new child relationships. Message IDs are caller supplied and globally unique in `session_message` ([SQL schema, lines 79–96](../../opencode/packages/core/src/session/sql.ts)); exporting the live root and importing under a new ID with unchanged message IDs would also collide. Rewriting those IDs and nested references would produce a copied conversation with different identity and substantial transformation code. The existing root's native Planner/slot children would still point to the original root.

The transfer commits one `session.created` operation and inserts imported message rows directly with assigned sequences; it does not replay ordinary per-message/step/inbox events ([transfer, lines 89–153](../../opencode/packages/core/src/session/transfer.ts)). Schema validation and database uniqueness still apply, but normal live execution lifecycle is not replayed. It has no idle-session precondition because it creates a new ID. Importing while an existing root has finished one turn still returns 409 for that root; export → transform → import cannot preserve its ID. Deleting the root first to reuse its ID would destroy its canonical history and live session identity, with routing, child-reference, race, and history-reconstruction hazards. A new imported root would require explicit TUI navigation, as the prototype does, and would leave the true M2-bound root behind. Exporting while ordinary writes continue can produce an obsolete snapshot; import has no compare-and-append precondition for the existing root.

An imported completed assistant is ordinary rendered conversation data and can enter the later root model context ([TUI part renderer](../../opencode/packages/tui/src/routes/session/index.tsx), [LLM lowering, lines 301–302](../../opencode/packages/core/src/session/runner/to-llm-message.ts)). The API is described and implemented as complete session transfer, not live transcript mutation. The hybrid prototype explicitly generated unused root and message IDs, supplied fictional user and assistant messages, and navigated to that new root ([prototype](../../opencode-agents-hybrid-ux-prototype/.opencode/plugins/hybrid/tui.tsx)). Its visual success is consistent with these semantics.

The same public route is available to a shell-capable Implementer via ordinary client/HTTP or the installed `opencode session import` CLI ([CLI source](../../opencode/packages/cli/src/commands/handlers/session/import.ts)). That fact alone is **not** a CAP break: conversation is non-authoritative, and a trusted projection would be bound to exact root/message/content and strict current history. Here the decisive problem is more basic: import cannot add one trusted row to the **existing** bound root. It would require copied-session routing, ID rewriting, reparenting, and revised M2 identity checks, while introducing model-context content and transfer coupling. There is no narrow `H0 + P` extension of current M2 history through this route.

**SESSION.IMPORT IS NOT SUITABLE FOR LIVE PROJECTION** — it rejects the already-existing root session ID.

## 5. Other viable mechanisms

**Direct public append or transcript row:** None appears in installed 2.0.17 client/TUI declarations or v2.0.18 route and TUI row source. `session.update` cannot change messages; the only message endpoints are reads. The TUI's row reducer is internal and derives rows from session messages and pending input. A hypothetical plugin-owned row could meet the selected visual layout without persistence or model context, but the target host exposes no public transcript-region anchor. Claiming `before: "session.composer.top"` would render a sibling *outside* the scrollbox, not a naturally scrolling row ([session view, lines 1416–1463](../../opencode/packages/tui/src/routes/session/index.tsx)).

**Synthetic:** `session.synthetic` admits an inbox item with caller ID, text, description, metadata, delivery, and `resume`; default behavior wakes execution ([core, lines 274–313](../../opencode/packages/core/src/session/session.ts)). The TUI renders a nonblank `description` as a notice; the `text` is lowered as **user-role** model input after delivery ([rows, lines 241–257](../../opencode/packages/tui/src/routes/session/rows.ts), [LLM lowering, lines 284–285](../../opencode/packages/core/src/session/runner/to-llm-message.ts)). `resume:false` on an idle root leaves pending inbox state that the current M2 idle check rejects and later execution may deliver. Cancel removes a still-pending item, including its optimistic display; once delivered it persists and cannot be canceled from history. A known input ID or event-derived message ID improves identification but changes none of these properties. A description-only item still has model-facing text and lacks ordinary assistant presentation. No supported configuration gives durable, display-only exact plan content.

**Trusted prompt/model echo:** `session.prompt` has `resume:false`, not `noReply`/`silent`/assistant insertion. With `resume:false` it is a pending user input; with normal resume it delivers a user message and starts/resumes model execution ([protocol, lines 392–410](../../opencode/packages/protocol/src/groups/session.ts), [core, lines 146–176](../../opencode/packages/core/src/session/session.ts)). An Orchestrator echo would require an extra model turn after M2's exactly one completed parent turn, violate the current parent shape, and depend on model byte-for-byte reproduction. Exact post-hoc comparison could prevent a wrong grant, but cannot guarantee presentation, costs another call, and repeats the trailing-whitespace/model-copy failure class. Supplying the candidate as a user message would show user-role input and perturb the root context. There is no simpler prompt mode that yields a trusted assistant transcript message.

**Internal append:** `SessionMessageUpdater.Adapter.appendMessage` is private to core projection, and `SessionProjector.insertMessage` is a non-exported function taking a durable event and database connection ([updater, lines 6–18](../../opencode/packages/core/src/session/message-updater.ts), [projector, lines 228–248 and 386–401](../../opencode/packages/core/src/session/projector.ts)). The host can produce assistant rows through `session.step.started`, text events and `session.step.ended`; these are the model-step event protocol, not a presentation append operation ([event schema, `Step`](../../opencode/packages/schema/src/session-event.ts), [updater, lines 214–271](../../opencode/packages/core/src/session/message-updater.ts)). `session.message.content.updated` is explicitly replay-only for older releases and updates an existing assistant; it cannot create one ([event schema, lines 145–156](../../opencode/packages/schema/src/session-event.ts)). Publishing fabricated step events would imply a fake model execution and couple CAP to event sequencing, runner state, and TUI incremental rendering. Importing core services or TUI row files directly from a project TUI plugin would cross the packaged plugin/context boundary and require host runtime/service wiring; the installed project does not have `@opencode/core` as a dependency. An unannounced direct database row also lacks a normal event for active TUI rendering. No small, well-defined internal function can be called by this plugin to cleanly append one settled assistant presentation message. The internal coupling is therefore not justified as a production recommendation.

## 6. Projection binding and M2 transcript implications

Current M2 binds a single exact parent history `H0 = JSON.stringify(parentHistory)`, and later checks full equality, plus exact Planner/slot histories, session identity/outcome/idle/inbox, location, candidate integrity and Git freshness ([M2 binder, lines 37–63 and 138–183](../src/m2/attempt.ts), [admission, lines 212–261](../src/m2/attempt.ts)). `parentCalls` permits one root user input, exactly two native calls, one idle marker and a final assistant. Its `oneFinal` check rejects a later assistant even if that row has no `finish: "stop"`, because the last assistant would change ([M2 parser, lines 63–70 and 91–110](../src/m2/attempt.ts)). A canonical projection therefore needs a deliberate expected post-idle extension, not another Orchestrator/model turn.

The minimal contract for a future supported append or transcript-row API is:

```text
H0 = complete original root history, already M2-bound
C  = frozen candidate with encoding and digest
T  = deterministic full presentation(C), preferably candidateMessage(C)
P  = trusted append/render result bound to root ID + unique row/message ID
verify observed root/row == H0 followed by exactly P, with P.text == T
H1 = complete resulting root history (or H0 plus an exact UI-row identity)
enable root-only local strip for C
on unexpected root event, route change, row loss, content/ID change: STOP
on Authorize callback: re-read/reverify H1 and P, candidate, generation,
  bound children, idle/inbox, root/HEAD and Git freshness; grant C once
```

For a canonical append, bind **session ID, host-confirmed message ID, type, complete content (and any presentation metadata), position after `H0`, candidate digest and exact formatter output**. Capture `H1` only after reading back the append and confirming it is the sole extension. The existing `parentCalls`/`oneFinal` parser must continue to validate the exact `H0` prefix; post-projection gates compare the *entire* observed history with `H1` and validate `P` separately. Passing full `H1` back into the old `parentCalls` would incorrectly parse the trusted presentation row as another model assistant. Recheck `session.message.get` by ID and compare the complete message as well as the full ordered history at the callback and existing later M2 checkpoints. A caller-chosen ID, if allowed, is an identifier, not origin proof: trusted code must associate it with its own call result and read-back, check `H0 → H1` exactly, and fail on conflict or ambiguity. Do not accept arbitrary suffixes, partial field comparison, or semantic matching. If a future API returns an ID but the active TUI has not yet displayed it, a host-backed render acknowledgment or an equivalent local visibility gate is needed before enabling Authorize; a database read alone proves persistence, not what was shown on screen.

For a future **transcript-region UI row** that is not canonical history, retain strict `H0` for the root, bind a plugin-private row ID and exact rendered text to `C`, and require the row mounted in the current root generation before enabling the strip. Root/child navigation can remount only if the same activation-private candidate remains live and is revalidated; leaving the root while a decision is pending should settle STOP under the selected local-callback lifecycle. Plugin reload revokes the generation and removes that row/control. A canonical appended message would survive reload as presentation but could never restore its old callback or one-use grant. Persisted text is not persisted CAP authority.

Any unexpected message before projection prevents `H0 + P` verification. Any message after projection changes `H1` and disables/aborts authorization. A forged visually similar plan in a different session, user input, notice, or assistant response is not `P` merely because it contains the same words. Current exact child/session/Git checks remain intact.

## 7. Threat analysis

This is the accepted V1/M2 trust model, not a requirement that no one else can write conversation text. The central question is whether a nontrusted actor can make the **active local strip** authorize candidate `C` while the user sees a forged or stale projection.

| Actor | Transcript/API access relevant here | Forged/stale projection path and required disposition |
| --- | --- | --- |
| Trusted OpenCode host/TUI | Owns history projection, renderer, routing and event delivery. | In the TCB. A future append API must return a stable ID and support read-back/visibility binding. |
| Trusted active `opencode-agents` TUI plugin | Owns `C`, digest, original/extended history snapshots, row identity, local callback and generation. | Must activate the strip only after exact projection verification and revoke/STOP on mismatch. A stale callback after cleanup cannot grant. |
| Local human / trusted local client | Can type, navigate, prompt sessions, and call public APIs. | May create other messages or a new imported session. The chosen root ID and whole-history check distinguish them; ordinary trusted-local activity outside CAP is allowed by the threat model. |
| Orchestrator model | Has the narrow native Planner/slot call permissions and can produce prose in its own completed turn. | Its prose is model output, not `P`; M2 binds exact root history/calls. A further turn or altered root history fails idle/history/shape checks. It has no local Authorize closure. |
| Planner / `implementer_slot` | Read-only native children produce child messages; Planner text is parsed into `C` only by trusted code. | They cannot invoke a trusted projection API or callback. Changed child output/history fails M2 binding. Their prose cannot itself authorize. |
| Current or prior shell-capable Implementer | Can invoke supported client/CLI HTTP routes, including import, prompt, synthetic, session navigation/commands, and could leave a background process. | Can create a *different* imported session, or add/pending root input if it knows the ID. It cannot import over the existing root, cannot address the unregistered local callback, and cannot use a public assistant append. Strict root ID, `H1`, active/inbox and route checks must STOP on its interference. A new session with similar text cannot carry the root-scoped strip. |
| External same-user process outside model control | Can use ordinary local client/CLI APIs; deliberate TCB modification/OS input spoofing is outside V1. | Same transcript interference is caught by ID/history/freshness checks before CAP admission. It is not assumed to be a cryptographic adversary to trusted local UI code. |

If a future API allowed a shell actor to choose assistant content and message IDs, ID alone would not establish provenance. The narrow safe claim is that the active plugin initiated one append while `H0` was exact, read back a unique `P` and exact `H1`, and rechecked them immediately before grant. Concurrent same-user changes may deny service; they must not be silently accepted as the frozen plan. A model actor's ability to create *other* transcript text is therefore not by itself disqualifying. Conversely, a proposed surface that lets it replace `P` or leave the strip active while displaying different content is disqualifying.

## 9. Recommended smallest production architecture

**No current public production mechanism projects the exact candidate as an ordinary row in the live existing root transcript.** The minimal next action is to request/add one narrowly scoped OpenCode host capability: append one settled, explicitly presentation-originated transcript row to an idle existing session (or mount one plugin-owned row after a specified message inside the normal transcript scrollbox), return its stable identity, and expose reliable read-back plus visibility/route semantics. Prefer a public supported API. A display-only transcript row would avoid later model-context effects; if the host instead appends a canonical assistant message, document that future root model turns will see it. Neither form may create CAP authority. The host API should not be synthesized from fake model-step events or a session-transfer copy.

With that primitive, the production sequence is: bind `H0` and children → freeze `C` and deterministic `candidateMessage(C)` → append/mount `P` on the same root → read back exact ID/type/content and verify sole expected extension/visible root → freeze `H1` → show compact `Plan <digest prefix> · HEAD <HEAD prefix>` strip with local Authorize/Cancel → on local affirmative callback reverify `P`, `H1`, candidate, liveness and existing M2 freshness/bindings → grant and consume once. Include exact file count only if it fits the strip without obscuring identity; intent summary is unnecessary there because the full intent and plan are in `P`. Digest and HEAD are trusted deterministic values from [`makeCandidate` and `candidateMessage`](../src/m1/proposal.ts), not values parsed from conversation text. The strip's identity helps a human notice a stale view; full machine equality is still required.

The same canonical append, if supplied, is **naturally reusable** later for trusted M2 PASS/STOP as ordinary root evidence. That later result has no Authorize control and needs its own exact result content/binding; it is not a blocker for plan projection. A client-local row API would be only **possible but separate** for PASS/STOP because it would disappear on reload. This report does not design Review or Commit.

## 10. Required proof before implementation planning

**NO ADDITIONAL PROBE REQUIRED** to decide the present host surface: v2.0.18 source decisively shows import's existing-ID conflict, synthetic/prompt inbox semantics, the public slot map, and the absence of a live message append route. Running a disposable import probe would not change those conclusions. Once a new host primitive is specified or delivered, its implementation planning should require focused proof of same-root ID/content read-back, active TUI rendering and reload/navigation behavior, model-context semantics, and strict `H0 + P` verification. That is proof of a future API, not an unresolved runtime fact in this investigation.

## 11. Likely implementation surface

After the host exposes a suitable capability, [`src/m2/attempt.ts`](../src/m2/attempt.ts) would freeze and bind `P`/`H1` around its current candidate and admission path; [the TUI plugin](../.opencode/plugins/opencode-agents/tui.ts) would own the compact root-only local callback and generation cleanup; [`src/m1/proposal.ts`](../src/m1/proposal.ts) already provides the deterministic full candidate and identity values. The matching OpenCode host layer would be its session projection/public client route **or** transcript row slot, with the relevant client declaration. These are likely files/modules, not an implementation plan. No implementation file was edited.

## 12. Open blockers

- The target host lacks a supported operation or slot that places an exact trusted row in the live existing root transcript and returns/binds stable projection identity with observable display semantics.
- The choice between a durable canonical message (later model context) and a display-only transcript row (generation-local) belongs to the host API contract. Both can preserve CAP if exact presentation and visibility can be bound; neither is currently exposed.

CURRENT OPENCODE HOST HAS A TRUSTED TRANSCRIPT-PROJECTION API GAP
