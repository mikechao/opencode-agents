# Milestone 2 native-child authority handoff investigation

## 1. Executive conclusion

**Classification: NOT COMPATIBLE WITH CURRENT CAP BOUNDARY.** Current OpenCode can create a native, clickable, initially read-only child and the trusted TUI plugin can later prompt that exact child. It can also switch the child's agent. The missing primitive is an **atomic, one-turn agent/permission selection**: `session.prompt` has no executing-agent override, while `session.switchAgent` and `session.update({permissions})` change durable session state. A child switched or unlocked for implementation remains independently promptable if the TUI generation disappears. Restoring the role or permissions afterward cannot close the crash window and may alter an in-flight turn. A server-side getter can avoid putting the proposal in the launch prompt only by moving authority across the TUI/server boundary. None of these is a small current-API composition satisfying all twelve required properties. ## 2. `codex-agents` reference mechanism

The current predecessor's exact route is **native Plan primary → native Planner child → persisted PlanArtifact → Plan's exact presentation and approval → execution-only Orchestrator → Workflow snapshot → native Implementer child**. ## 4. Trusted second-turn / agent-switch analysis

**Candidate 1 works as an API sequence, but fails as authority.** A read-only `implementer_slot` child can be launched by the Orchestrator, complete one innocuous turn, and yield a child ID in the parent subagent result. After CAP confirmation, TUI code could call `session.switchAgent({sessionID: exactChild, agent: "authorized_implementer"})`, then `session.prompt({sessionID: exactChild, text: exactFrozenPrompt})`. This is the supported equivalent of the proposed conceptual `prompt({agent: ...})`; the prompt operation itself does **not** accept that field. Source shows the switch writes `SessionEvent.AgentSelected`, which updates `SessionTable.agent` and appends an `agent-switched` history message. The runner then selects the stored agent and its tool/permission snapshot. [Host: `../opencode/packages/client/src/effect/api/api.ts:SessionSwitchAgentInput,SessionPromptInput` lines 238–279; `../opencode/packages/core/src/session/session.ts:switchAgent,prompt` lines 90–96, 145–177; `../opencode/packages/core/src/session/projector.ts:AgentSelected` lines 546–555; `../opencode/packages/core/src/session/message-updater.ts:AgentSelected` lines 90–102; `../opencode/packages/core/src/session/context.ts:select` lines 121–156.]

The switch changes **session identity persistently**, not just one prompt. The child keeps `parentID`, and the later assistant messages identify their selected agent, but the session's current agent becomes `authorized_implementer`. The Orchestrator's `subagent:authorized_implementer = deny` blocks a *native subagent call naming that target*, including continuation, because the tool asserts permission before looking up or switching an existing child. A permitted continuation naming `implementer_slot` would switch that child back to the read-only agent first. These are useful parent-side restrictions, provided no broad session override defeats them. They do not make the child safe: the public client/TUI can prompt the child directly by ID, and a native child's route has a normal prompt UI. On a crash after the switch, the child remains implementation-capable for another input; the stored role, not CAP, would authorize the tools. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 134–181; `../opencode/packages/core/src/session/projector.ts:AgentSelected` lines 546–555; `../opencode/packages/tui/src/routes/session/index.tsx` lines 1463–1523; `../opencode/packages/core/src/permission.ts:configured` lines 158–163.]

Restoring `implementer_slot` after `session.prompt` returns is unsafe. That API returns after **input admission and wake**, not after the whole model turn. The runner reads the agent at a later context boundary and refreshes context on later steps/retries. An immediate restore can make the approved input execute partly or entirely read-only; waiting for `session.wait` leaves a durable implementation-capable interval during which the TUI could die. Even a tightly timed restore has no atomic compare-and-swap against an input ID or guarantee that already selected tool calls are canceled. This is a source-supported race/lifetime objection; its exact UI timing was not probed. [Host: `../opencode/packages/core/src/session/session.ts:prompt,wait` lines 145–177, 266–269; `../opencode/packages/core/src/session/runner/llm.ts:advanceToStep,prepareContext,runStep` lines 162–178, 185–239; `../opencode/packages/core/src/session/runner/step.ts:attempt` lines 83–129.]

## 5. Permission-unlock analysis

**Candidate 2 fails more directly.** A read-only slot can use deny rules for `edit`, `shell`, `execute`, `subagent`, mutating custom tools, and all relevant Git/history operations. `edit` denial alone is insufficient because shell or a custom tool can mutate. Read-only shell should be denied entirely or constrained to a checked finite allowlist. The bootstrap turn is mechanically harmless only after reviewing its **effective** agent plus inherited session rules and every exposed mutation route. Before CAP, no implementation-capable turn or executable proposal is delivered. A model's harmlessness instruction is not a permission control. [Host: `../opencode/packages/core/src/session/context.ts:select` lines 127–142; `../opencode/packages/core/src/permission.ts:configured,evaluateInput` lines 158–188; `../opencode/packages/schema/src/agent.ts:Info.default` lines 39–53; project: `docs/charter.md:Authority` lines 36, 85–89.]

`session.update({permissions})` replaces the child's session rules and persists them. Because those rules are evaluated after agent rules, an allow can override the slot agent's deny. This produces a session-wide permission window, not one bound to the frozen proposal, prompt ID, tool call, or TUI generation. A crash between allow and revoke leaves the permission record; a later direct prompt or native continuation under an agent with those permissions can reuse it. If a model has emitted multiple tool calls, separate tool fibers can pass permission assertions during the window; revocation does not undo an assertion already admitted. Queued input can also be promoted against whichever rules are then current. The API has no atomic one-input unlock/relock transaction or consumption bit. [Host: `../opencode/packages/client/src/effect/api/api.ts:SessionUpdateInput` lines 250–257; `../opencode/packages/server/src/handlers/session.ts:session.update` lines 255–278; `../opencode/packages/core/src/session/projector.ts:Permissions` lines 584–590; `../opencode/packages/core/src/permission.ts:assert` lines 231–263; `../opencode/packages/core/src/session/runner/step.ts:attempt` lines 83–129; `../opencode/packages/core/src/session/runner/llm.ts:advanceToStep` lines 78–101, 162–178.]

OpenCode's `edit` rules can name resources, but an allowed general shell or `execute` path can change files outside an edit-path rule. The current M1 exact-file scope is enforced by trusted **post-implementation Git observation**, with its documented ordinary-observation limits, rather than by agent permission path rules. Session unlocking cannot bind the exact plan/root/HEAD or replace that gate. Therefore “revoke afterward” is incompatible with CAP even if the ordinary successful run happens to revoke promptly. [Project: `src/m1/attempt.ts:runM1` lines 175–194; `docs/coding-authority-protocol.md:M1 scope` lines 309–354; host: `../opencode/packages/core/src/permission.ts:evaluate` lines 87–101.]

## 6. Child-fetch analysis

**Candidate 3 cannot directly read TUI-private CAP state.** TUI `client` calls and events can submit/read session inputs and display a dialog. The model-callable tool callback, `tool.execute.before`, server plugin command, permission/question handling, and MCP tool executor are server-side surfaces. The TUI keymap command that owns M1's generation closure is not callable as a model tool. A server getter has no current supported reference to that closure or synchronous request/reply operation that proves its exact confirm result and one-use consumption. A question or generic permission reply is not the frozen-candidate CAP binding; the latter can be answered outside the CAP plugin and carries no exact proposal. [Host: `../opencode/packages/plugin/src/tui/context.ts:Context,KeymapCommand` lines 384–409, 516–532; `../opencode/packages/plugin/src/effect/plugin.ts:Context` lines 26–54; `../opencode/packages/plugin/src/effect/tool.ts:ToolHooks,ToolDomain` lines 20–59; `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 138–151; `../opencode/packages/core/src/permission.ts:assert,reply` lines 231–319; project: `src/m1/attempt.ts:grantIntent,consumeIntent` lines 21–33.]

Making `get_authorized_implementation` work would require copying a proposal/grant into server or MCP state, a cross-process request/reply authority protocol, or a bearer/signed capability with server-side verification and consumed-state handling. These are precisely the shared or durable authority arrangements the charter excludes. A server getter that merely returns a proposal after a model-supplied `approved=true`, workflow ID, or other conversation token is not CAP. A server that gates only the getter still needs to mechanically prevent the native child from ordinary edits/shell before the getter; the old Implementer role did not. [Project: `docs/charter.md` lines 3–5, 36, 63–69; `docs/coding-authority-protocol.md:Process-scoped authority` lines 269–307; reference: `../codex-agents/.opencode/agents/implementer.md` lines 5–11, 122–136.]

**A random model-visible token does not fix the boundary.** The token can be copied into another call or child, replayed after continuation/reload, and used multiple times unless the server tracks exact use. Marking it consumed on the server requires durable/atomic policy if process restarts matter; leaving it in the TUI closure requires a cross-process verified call into that closure. A signed token only authenticates bytes; it does not bind one exact active TUI generation, one child, one input/turn, freshness, and single consumption without additional verifier state. Token presentation would make model-visible state the effective authorization input, contrary to the charter's rule that model-supplied tool arguments grant nothing. ## 7. Authority lifetime and replay analysis

For **any** native-child proposal, the TUI would have to bind one active attempt's Orchestrator session and request/message ID; one native `subagent` tool part/call ID; a fresh child ID whose `parentID` equals that Orchestrator; the child's first harmless input and final result; the exact Planner proposal; and CAP's candidate digest, canonical root, HEAD, confirmation result, and consumed grant. After the freshness recheck, it would have to send exactly one trusted frozen implementation input, record its returned input ID, reject duplicate/synthetic/shell inputs and unexpected agent turns, wait for one successful bound result, then apply M1's Git scope gate. Another child, stale attempt, model-supplied ID, extra tool call, changed proposal, dirty root, or changed HEAD must stop. Parent tool metadata and session-family data are useful **identity evidence**, not admission authority. [Project: `src/m1/attempt.ts:completedText,runM1` lines 84–119, 121–198; host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 153–265; `../opencode/packages/schema/src/session-message.ts:AssistantTool` lines 138–174.]

Native launch lacks an atomic TUI child-ID callback. The TUI could source-bind one completed parent tool part, inspect its `metadata.sessionID`, call `session.get`, and reject any extra or mismatched child; this is **possible by source inspection, not runtime-proven**. It cannot turn that observation into a one-turn permission grant. Direct `session.prompt` or `session.synthetic` can supply trusted exact text and return an input ID, but both are ordinary conversation input unless the executing agent/permissions are mechanically gated. An idempotent supplied message ID prevents accidental duplicate insertion of that same ID; it does not stop another prompt ID or another caller from resuming a capable child. [Host: `../opencode/packages/client/src/effect/api/api.ts:SessionPromptInput,SessionSyntheticInput` lines 267–313; `../opencode/packages/core/src/session/session.ts:prompt,synthetic` lines 145–177, 274–313.]

**TUI-generation death is decisive:**

| Candidate | Immediately after admission if TUI generation dies | CAP verdict |
| --- | --- | --- |
| Agent switch | An already admitted model turn may finish, **and** the child's stored agent may remain `authorized_implementer` for a new prompt. A later TUI generation sees the same session state. | Fails one-use and zero-reusable-authority requirements. |
| Permission unlock | An admitted turn may finish, **and** the child's durable allowed session rules may remain. Pending/previously permitted tools are not recalled by a later deny. | Fails one-use and zero-reusable-authority requirements. |
| Child fetch | If server/MCP stores a grant/token/approved view, it may outlive the TUI generation unless a new cross-process lifetime/consumption protocol is built. If it stores none, the getter cannot authorize the child. | Fails current boundary or cannot operate. |
| Trusted root M1 | The consumed TUI-local grant is gone. Only the already admitted exact root Implementer turn may finish; a later generation starts with no usable grant. | Matches current CAP lifetime. |

This table concerns **CAP authority**, not isolation from an operator or malicious same-user process that can directly change local OpenCode state. The charter trusts the installed host and local OS/user boundary; it does not turn model-visible session state into CAP authority. [Project: `docs/charter.md` lines 65–69; `docs/coding-authority-protocol.md` lines 47–59, 269–307; `.opencode/plugins/opencode-agents/tui.ts:setup` lines 7–37.]

M1's one-use claim is about **CAP admitting one prompt**, not an OpenCode-wide prohibition on all future direct session input. The proposed native-child invariant in this task is stricter about an old child retaining a reusable implementation-capable role. Neither a durable role switch nor a durable permission unlock satisfies that stricter invariant. ## 9. Smallest viable M2 shape
