## 2. Current M2 UX and binding map

The TUI plugin takes a clean Git snapshot at activation, remembers one newly created root `opencode-agents` session, and starts `runM2` on that root's successful execution event. Failure or interruption raises an ephemeral STOP alert; cleanup synchronously sets `generation.revoked` ([`tui.ts`](../.opencode/plugins/opencode-agents/tui.ts), lines 6–45, 73–80). The primary's instructions make it call native `subagent` twice: Planner with `User request:\n` plus the exact user text, then a fixed `implementer_slot` bootstrap ([`opencode-agents.md`](../.opencode/agents/opencode-agents.md), lines 1–11). Both children are read only by their role rules; the authorized role permits edit and ordinary shell ([agent definitions](../.opencode/agents/)).

After the parent finishes, trusted code verifies the root is one plain user input, exactly two sequential completed native calls, distinct tool/child/message IDs, exact call arguments, child parentage/agent/location/outcome/idle/permissions, each child's sole bootstrap input/final/idle result, and exact parent tool-result wrappers ([`src/m2/attempt.ts`](../src/m2/attempt.ts), lines 37–164). It freezes `makeCandidate(parseProposal(plannerChild.text), root, head)`. [`src/m1/proposal.ts`](../src/m1/proposal.ts), lines 52–101, validates the exact `intent`, `plan`, and file set, encodes root and HEAD, computes a SHA-256 digest, and deterministically formats the complete decision text.

`runM2` then requires the candidate text to fit the terminal and passes **that text** to `context.ui.dialog.confirm` with `Authorize` / `Cancel` labels, enlarging the blocking modal. It accepts only `true`; after confirmation it checks candidate integrity, display fit, parent/child binding, current location and clean bound Git baseline. It calls `grantIntent`, switches the exact slot child to `authorized_implementer`, rechecks the switched child and frozen parent/Planner, consumes the grant, and issues exactly one trusted `session.prompt` with the frozen candidate. It binds the returned prompt ID/text and completed child transcript, then applies the M1 unchanged-HEAD/exact changed-path gate ([`src/m2/attempt.ts`](../src/m2/attempt.ts), lines 212–265; [`src/m1/git.ts`](../src/m1/git.ts), lines 39–72). PASS and STOP are `dialog.alert` calls in [`tui.ts`](../.opencode/plugins/opencode-agents/tui.ts), lines 29–45. They disappear on dismissal. The live report says the PASS modal had to be dismissed to inspect the child and a repeat was used to capture both pieces of evidence ([`milestone-2-live-dogfood.md`](milestone-2-live-dogfood.md), lines 98–105, 184–200).

The current exact-history guard is `JSON.stringify(parentHistory) === bound.parentHistory` before and after confirmation and after the slot switch; analogous complete-history comparisons protect Planner and slot bootstraps ([`src/m2/attempt.ts`](../src/m2/attempt.ts), lines 138–183, 185–207). The root user message ID, native parent assistant/tool IDs, child session/input/final IDs, candidate encoding/digest, baseline root/HEAD, and generation-local grant are already available. A trusted presentation event inserted into the parent **after the first freeze** would invalidate the current whole-parent equality; the check would need a deliberate expected extension, not a broad exemption.

## 4. Trailing-whitespace root cause and trust analysis

The failed live attempt used root session `ses_f19d0ec7affeBg3GctNjMI3Yte`: the stored root `user.text` ended in one U+0020 after the final period; the stored parent `subagent` tool input's `prompt` lacked that terminal U+0020. The exact predicate in [`src/m2/attempt.ts`](../src/m2/attempt.ts), lines 104–109, rejected it before presentation/admission. This is the strongest observed byte evidence; the original keystroke/provider frames were not captured ([`milestone-2-live-dogfood.md`](milestone-2-live-dogfood.md), lines 137–165).

OpenCode's TUI calculates a trimmed copy for blank/exit detection, then builds the submitted prompt from untrimmed `store.prompt.text` ([host `component/prompt/index.tsx`](../../opencode/packages/tui/src/component/prompt/index.tsx), lines 1111–1135). Core `Session.prompt` passes input through `SessionPrompt.prepare`, whose user payload takes `input.text` without a `trim` ([`session.ts`](../../opencode/packages/core/src/session/session.ts), lines 146–175; [`prompt.ts`](../../opencode/packages/core/src/session/prompt.ts), lines 39–85). The native subagent input schema declares `prompt: Schema.String`; its implementation passes `input.prompt` into the child unchanged except for a fixed prefix and stores the call input in the parent tool part ([host `subagent.ts`](../../opencode/packages/core/src/tool/plugin/subagent.ts), lines 29–48, 200–218; [`src/m2/attempt.ts`](../src/m2/attempt.ts), lines 75–89, 112–115). The provider adapter parses JSON tool input; the inspected shared parser has no terminal-whitespace canonicalization rule ([host `shared.ts`](../../opencode/packages/ai/src/protocols/shared.ts), lines 180–185).

Therefore divergence is already present **at the model-authored tool argument observed by M2**. The available evidence does not distinguish model generation from provider tool-call serialization/decoding at a finer boundary. It does exclude a demonstrated OpenCode root-message trim or native subagent transport trim in this case. Do not claim a precise provider-level root cause without a captured stream. The current equality proves that the Planner saw the exact root user bytes through the model-authored call, not merely that the child and tool row agree with each other. Host session/tool IDs alone cannot prove content equality: they identify the transport objects, while the model can choose their prompt content. A `.trim()` or other silent canonicalization would accept a changed request and obscure the mismatch.

The byte-copy property can instead be obtained by **trusted construction**. Keep a fresh native read-only Planner child, but make the Orchestrator's native Planner call a fixed harmless bootstrap (and verify it as exactly such). After the root completes and the binder verifies native parent/child identities, trusted TUI code reads the already bound root `user.text`, constructs `plannerInput(rootText)`, and issues one `session.prompt` to that exact Planner child. Bind the returned input ID and exact text, child agent/parent/location, idle/no-pending status, one new final result and no extra input; build the candidate from that new Planner final. The plugin already performs the analogous exact trusted prompt/returned-ID binding for the Implementer ([`src/m2/attempt.ts`](../src/m2/attempt.ts), lines 248–258). The parent native tool result would then attest only the harmless Planner bootstrap, while the trusted continuation attests the actual planning input. This uses no normalization and no new authority kind. It adds one read-only Planner turn and requires a narrow rewrite of Planner transcript expectations. A directly TUI-created `session.create({parentID, agent:"planner"})` child is another public API route, but would replace more of the settled native Orchestrator call shape; the same-child trusted continuation is smaller.

The exact canonical boundary is the host-stored root `user.text` read under its bound message/session ID. Preserve every code unit of that string in trusted construction and verify the returned/persisted child input exactly. IDs then bind *which* user and child messages were used; content equality binds *what* was sent. The worktree/root/HEAD/candidate freshness checks still apply. This is a source-supported design hypothesis, not a completed runtime proof (§8).

## 5. `codex-agents` UX lessons

The read-only predecessor's [`workflow-mcp/README.md`](../../codex-agents/.codex/workflow-mcp/README.md), lines 16–35, and [`.codex/agents/WORKFLOW.md`](../../codex-agents/.codex/agents/WORKFLOW.md), lines 87–114, describe a parent Plan conversation that fetches an authoritative plan revision, presents `full_plan` verbatim, and treats the user decision separately. Its source has `plan_parent_get`/`plan_approve` and a SQL-backed `PlanStore` with revision and approval rows ([`server.ts`](../../codex-agents/.codex/workflow-mcp/server.ts), lines 308–375; [`plan-store.ts`](../../codex-agents/.codex/workflow-mcp/plan-store.ts), lines 32–67). That is a UX reference, not a host API proof or architecture template.

**Carry forward**

- Show the complete authoritative plan/proposal in the parent context before asking for a decision; use a short, separate `Authorize`/`Cancel` action.
- Show a stable human-readable intent, exact file scope, root, and HEAD; keep opaque IDs/digests in trusted binding or optional diagnostics.
- Keep the decision and final PASS/STOP easy to revisit while navigating the native child. Conversation may present exact trusted content without becoming the authority store.

**Do not copy**

- Workflow MCP, its `PlanStore`/revision graph/approval rows, Workflow objects, phases, action descriptors, operator-decision dispatch, and parent/worker MCP plan tools.
- Persisted attempt state, linked follow-ups, retries, repair/recovery or reconciliation machinery, role-specific workflow views, or a replacement authority service.
- Model prose that merely claims to quote an authoritative plan. In this repository, a presentation can be trusted only when the plugin itself renders the frozen candidate, or when a future host API supports exact trusted insertion and the plugin verifies it.

## 7. Recommended smallest architecture

Use the current fresh root/native-child family. Change the model's Planner call to a fixed verified read-only bootstrap, then send the exact host-stored root request in a trusted prompt to the same Planner child and bind its new result. Freeze the candidate as today. Present `candidateMessage(candidate)` from activation-private state in a root-session-scoped TUI slot/panel. Keep it accessible while the authorization choice is pending and while navigating back from the child. Invoke the already accepted `ui.dialog.confirm` with a concise title and candidate digest/HEAD reference; the full candidate must be legible immediately before that choice. Accept only the promise's `true`, recheck liveness, candidate digest, displayed candidate identity, parent/Planner/slot bindings and Git freshness, then use the existing same-child switch, `grantIntent`, `consumeIntent`, one trusted Implementer prompt, and Git gate. Render PASS or STOP from trusted facts in the same root-scoped UI, with a toast if the user is viewing a child. Do not treat a UI row, toast, child role, or conversation text as authority.

```text
User request (root user message ID + exact stored text)
  → Orchestrator → native Planner bootstrap + native inert slot
  → trusted bind of parent/children → trusted exact prompt to same Planner child
  → trusted bind of Planner result → freeze candidate in this TUI generation
  → root TUI presents exact candidate → short trusted Confirm: Authorize / Cancel
  → candidate/transcript/root/HEAD/worktree freshness checks
  → existing one-use CAP grant → same-child Implementer switch and one prompt
  → bound child result → M1 Git gate → root TUI shows trusted PASS/STOP
```

Activation-private state needs the original baseline, root/user IDs and exact text, native tool/child IDs, immutable Planner and slot bootstrap snapshots, trusted Planner prompt ID/text/result snapshot, frozen candidate encoding/digest and rendered text, and the single-use grant. The displayed projection can include a digest as an identity cue; the plugin must compare the exact stored candidate/rendered text before using a confirmation. A TUI Confirm result is tied by its own lexical promise to this one candidate, not by a model-supplied or server-supplied token. Cancellation/dismissal, generation revocation, host shutdown, navigation away at decision time, changed candidate or worktree, ambiguous Planner/Implementer input, and stale UI must all stop before any new admission. Recheck location and that the complete candidate is actually available in the root UI at the moment of choice; if the UI cannot show it, fail closed rather than show a digest-only approval.

Host message/session/tool/form IDs are trusted as identities of host objects only. Their values and caller-supplied metadata cannot attest that a human approved content. Under the accepted local TUI trust boundary, a model cannot manufacture or replay the lexical `confirm` promise's affirmative return; it can at most cause trusted code to open a new dialog, which is not an approval. A stale dialog's answer must be discarded after generation, candidate, transcript, and Git rechecks. For a form, in contrast, even a correctly matched form ID and digest can be answered through the public client without a human gesture.

`grantIntent` and `consumeIntent` in [`src/m1/attempt.ts`](../src/m1/attempt.ts), lines 6–33, remain the process-local authority mechanics. The grant is `{digest,purpose,consumed}`; liveness and integrity are checked on creation/consumption, and `consumed` flips before prompt admission. Reload revokes the old generation and leaves any delivered UI projection as evidence only. The trusted Planner continuation requires adding its expected messages to the **Planner** frozen transcript; it need not relax the frozen **parent** transcript. If a later host-supported display-only parent event exists, compare a known old prefix plus exactly one event with a trusted ID, type, contents and candidate digest, then freeze that new boundary. Never switch to “ignore later parent messages” or trust a model echo. Persistent presentation and ephemeral CAP authority are conceptually compatible; this host version has not supplied a safe persistent transcript insertion path.

The final trusted report can contain bound HEAD, exact resulting path set, and STOP reason, because those come from the existing Git/result checks. In the recommended TUI projection they remain available through root/child navigation in the active generation without a blocking final modal. They do **not** survive TUI reload as normal conversation history and do not require a durable workflow record. A crash after the Git gate but before UI projection can lose that report; the worktree remains the trusted current reality for a later fresh attempt. The current `tui.ts` also has an early parent failure path; it must use the same non-modal STOP presentation when this UX is implemented.

## 8. Required proof before implementation

Only these bounded proofs remain necessary; use a disposable session/repository outside this checkout for host probes and no repository writes as probes.

1. In actual CLI 2.0.18 with installed plugin/client 2.0.17, render an exact multi-line candidate and a PASS/STOP through `session.composer.top` or a small `session.panel`; navigate root ↔ child, resize, dismiss/replace the short Confirm, and confirm whether the complete candidate remains legible at the decision moment. Record that reload loses the projection rather than claiming transcript persistence.
2. In a disposable read-only native Planner child, send `plannerInput(rootMessage.text)` through trusted `session.prompt` with a terminal space in the root text. Compare returned input ID/payload, persisted child user message and Planner result, parent bootstrap transcript, and absence of extra inputs. A `session.synthetic(resume:false)` probe may establish pending-row visibility/reload/delivery behavior, but it cannot by itself establish presentation-only semantics; source already shows eventual model input. Do not plan against a hypothetical append API.

## 10. Open questions / blockers

- **Requested durable root-transcript experience:** no public 2.0.17 plugin/client API found for appending trusted, presentation-only content as ordinary root conversation history. `session.synthetic` is not equivalent. This is the only host-surface blocker to the full preferred UX; the TUI fallback is deliberately session-local.
- **Actual TUI layout/lifecycle:** source establishes slots, panel, and Confirm behavior but not that a long candidate is readable while navigating child sessions on the installed binary. The first bounded proof in §8 decides the exact native fallback presentation.
- **Fine-grained whitespace origin:** the observed two stored strings differ before native subagent transport; without provider frames one cannot assign the missing space specifically to model generation versus provider serialization. Trusted direct construction removes the dependency, so identifying that micro-layer is unnecessary for the proposed change.

The report is a decision aid. It does not authorize implementation, Reviewer design, Commit design, or a new durable workflow architecture.
