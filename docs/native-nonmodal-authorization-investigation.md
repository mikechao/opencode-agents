## 2. Settled authorization constraints

Form/Question is out: the public form list and reply endpoints let a previously authorized, shell-capable Implementer enumerate a pending form and submit `Authorize` via the supported `opencode api` route. Form validation checks answer shape and ownership, not TUI-origin provenance ([reassessment](native-question-cap-reassessment.md)). A form ID or candidate digest would bind *which* form was answered, but not *who* supplied the new CAP-positive answer.

The security reference is `ui.dialog.confirm`. `createDialogApi.confirm` creates a lexical promise in the TUI, passes `done(true)` only to the dialog's Confirm callback, `done(false)` to Cancel, and `done(undefined)` to dismissal/replacement ([host plugin API](../../opencode/packages/tui/src/plugin/api.tsx), lines 290–337). The widget invokes those callbacks from its mouse and key handlers ([Confirm widget](../../opencode/packages/tui/src/ui/dialog-confirm.tsx), lines 20–91). No session or Form reply ID addresses that promise. The current M2 code accepts only `true`, then checks generation, candidate integrity, transcript binding, location and Git freshness before creating and consuming a one-use grant ([M2 attempt](../src/m2/attempt.ts), lines 212–263). The modal obscures the plan and is therefore a fallback, not the target UX.

The relevant rule is that the affirmative callback must belong to the active trusted TUI/plugin generation, close over the frozen candidate, and have no positive-resolution route through model-accessible OpenCode host/client/server commands or session APIs. Physical-human attestation is outside V1.

## 3. `ui.slot` / `session.composer.top` evidence

**Render model.** The installed contract declares `SlotClaim.render(input) => JSX.Element`, with `append: "session.composer.top"` as a valid placement and `{sessionID}` as the slot input ([SDK context declaration](../node_modules/@opencode/plugin/dist/tui/context.d.ts), lines 150–231). The host mounts this slot directly above `Composer`, below the scrollable transcript ([session route](../../opencode/packages/tui/src/routes/session/index.tsx), lines 1387–1465). The plugin API registers the function in the active TUI registry and invokes it through a `PluginContextProvider`; it is a Solid component contribution, not a string template or server-rendered row ([host plugin API](../../opencode/packages/tui/src/plugin/api.tsx), lines 92–96, 270–283; [slot renderer](../../opencode/packages/tui/src/plugin/render.tsx), lines 80–140). It can return OpenTUI JSX such as `box`, `text`, and `scrollbox`, including custom child components. It has no supplied stock authorization button or built-in scroll policy.

**Interactivity and event path.** Host widgets use `box`/`text` `onMouseDown` and `onMouseUp` handlers as ordinary closures (for example [Confirm widget](../../opencode/packages/tui/src/ui/dialog-confirm.tsx), lines 71–88, and [session rows](../../opencode/packages/tui/src/routes/session/index.tsx), lines 1445–1455). A plugin's JSX can use the same direct event props. A pointer release is processed by the local OpenTUI renderer, which invokes the component's `onMouseUp` closure in the TUI process; that closure can capture activation-private candidate, digest, generation and a local resolver. No `context.keymap.layer`, `keymap.dispatch`, Form reply, session request, or command registration is needed for that path. Host JSX also uses `onKeyDown` on a focused text area ([prompt](../../opencode/packages/tui/src/component/prompt/index.tsx), lines 1745–1772), while some local views use `useKeyboard` ([error component](../../opencode/packages/tui/src/component/error-component.tsx), lines 65–85). The exact focused-key behavior for a *custom slot box* remains a small runtime question. A globally registered keymap authorization command would be unsafe and is unnecessary for the pointer path.

**Scope and navigation.** The slot input supplies the selected `sessionID`; the contribution should render the pending control only when it equals the bound root ID. The application keys `SessionFrame` by route session ID, so root → child unmounts the root frame and child → root mounts a fresh one ([app](../../opencode/packages/tui/src/app.tsx), lines 1363–1375). The slot renderer creates a component once per mount with reactive input getters and removes it when its claim or mount disappears ([slot renderer](../../opencode/packages/tui/src/plugin/render.tsx), lines 85–119). Thus component-local scroll/focus state is not a durable authorization store. Activation-private state could project the frozen candidate again on return, but a strict pending decision should instead settle STOP when the root decision view unmounts; the root can show the STOP result on return. The render function must check its input, not assume that a registered claim belongs only to the root.

**Length, resize, cleanup.** An unbounded candidate above the composer would consume the session's vertical space. A tiny wrapper needs a height-limited `scrollbox` for the full exact `candidateMessage`, with the decision controls fixed outside that scrollbox. The host uses `scrollbox` with `maxHeight`, and native layout measures sizes on resize ([Form review](../../opencode/packages/tui/src/routes/session/form.tsx), lines 1075–1134; [session route](../../opencode/packages/tui/src/routes/session/index.tsx), lines 1387–1436). Source supports such a layout but does not prove its legibility at the minimum terminal size, scroll focus, or that its control stays visibly associated after a live resize. Below a readable width/height, the safe behavior is to remove/disable Authorize and STOP, not leave an affirmative button beside clipped text. Unregistering the claim removes its contribution ([plugin API](../../opencode/packages/tui/src/plugin/api.tsx), lines 123–135, 270–283); plugin deactivation clears registered slots ([plugin context](../../opencode/packages/tui/src/plugin/context.tsx), lines 208–229). A queued/stale event still needs a generation-and-decision guard in its closure.

## 4. `session.panel` evidence

**Render model.** `session.panel` is another public JSX slot. Its `PanelInput` has `name`, `sessionID`, `width`, `presentation`, `focused`, `focus`, `close`, and `toggleFullscreen`; `ui.panel.open(name)` targets the *currently selected* session ([SDK context declaration](../node_modules/@opencode/plugin/dist/tui/context.d.ts), lines 137–149, 168–177, 407–419; [plugin API](../../opencode/packages/tui/src/plugin/api.tsx), lines 202–215). `PanelHost` renders the slot within a focusable OpenTUI `box` and an interactivity provider ([panel host](../../opencode/packages/tui/src/component/panel-host.tsx), lines 8–64). Therefore it accepts custom `box`/`text`/`scrollbox` controls and direct local callbacks; it is not display-only. A claim must check both its chosen `name` and bound root `sessionID`, since all active claims compose at the slot.

**Focus, layout and navigation.** The host focuses the panel on opening/mouse down, gives it a right-hand pane, and provides commands for moving focus between session and pane. The pane can be resized; an ordinary split leaves the root session visible ([session frame](../../opencode/packages/tui/src/component/session-frame.tsx), lines 88–180, 261–382). The host changes panel presentation to `fullscreen` whenever available width is at most 80 columns, even if `"panel"` was requested ([panel state](../../opencode/packages/tui/src/context/panel.tsx), lines 10–40). Fullscreen hides the underlying session pane ([session frame](../../opencode/packages/tui/src/component/session-frame.tsx), lines 279–298). This violates the desired always-visible normal root view at narrow widths; a plugin could fail closed on that transition, but cannot force split through the public option. A panel itself supplies neither plan scrolling nor fixed controls; its small content component must do so.

The panel target is client-local state with a bound session ID. On any route change away from that exact session, the app closes it ([app](../../opencode/packages/tui/src/app.tsx), lines 584–597). The keyed session frame also unmounts its panel host. Returning to root does not automatically reopen it. Other host actions such as selecting a terminal or sidebar can close it ([session frame](../../opencode/packages/tui/src/component/session-frame.tsx), lines 93–129). The plugin must treat any close/hide while pending as Cancel/STOP and must not silently reopen a pending Authorize control. The `PanelInput.close` method and `ui.panel.close` are local TUI operations; no dedicated server endpoint addresses the panel's child callback or resolver. A model-accessible `tui.session.select` event can navigate away ([TUI event schema](../../opencode/packages/schema/src/tui-event.ts), lines 53–60; [app](../../opencode/packages/tui/src/app.tsx), lines 1275–1281), but that can only dismiss a correctly guarded pending decision, not affirm it.

**Input route.** A panel child `onMouseUp` is the same local component callback as in the composer slot. `PanelInput.focused` and `focus()` allow a component to scope keyboard behavior to panel focus. Exact custom focused-key behavior and usable scroll layout still merit the disposable probe. If the plugin instead registers `Authorize` as a keymap command, the positive callback becomes programmatically dispatchable and loses the needed provenance.

## 5. Authorization callback threat analysis

The viable shape is one activation-private frozen candidate and digest, one pending local resolver, and one active generation. The component receives only a closure that attempts to settle that exact decision. A direct `onMouseUp` calls the closure in process; the closure checks generation, bound root, candidate identity and unsettled status before producing `true`. After settlement, the plugin removes both controls and performs the existing M2 rechecks before `grantIntent`. Candidate data shown in JSX is presentation; it is not a grant.

| Actor | Access to a direct slot/panel Authorize closure | Effect under the accepted V1 model |
| --- | --- | --- |
| Trusted host/TUI | Owns renderer and calls component event props. | Inside TCB; can produce the local event. |
| Trusted active plugin | Owns candidate, resolver, generation and rendered closure. | May settle once, recheck, then create the grant. Reload revokes its old generation. |
| Local human / trusted local client | Can interact with the TUI. | Intended decision source. OS input automation and same-user TCB changes are outside V1. |
| Model-controlled Orchestrator | Can cause its permitted native child workflow to run; has no reference to the private closure or a permitted positive-resolution tool. | Cannot directly affirm the pending local callback. Its prose is never a decision. |
| Planner / `implementer_slot` | Read-only native children with no TUI callback reference. | Cannot affirm it. Their output can only become a candidate after trusted parsing/freezing. |
| Previously authorized shell-capable Implementer, including an earlier background process | Can use `opencode api`/`service`, session endpoints, and supported TUI event/command routes. | Can enumerate/reply to Forms and can dispatch registered commands or navigate the TUI; cannot address this unregistered in-memory closure through those APIs. It may cause dismissal/STOP, not Authorize. |

The server-exposed TUI event inventory includes `tui.command.execute` (arbitrary command string), `tui.session.select`, toast and prompt append, but no pointer/key injection or callback invocation request ([TUI event schema](../../opencode/packages/schema/src/tui-event.ts), lines 11–60). The TUI handles `tui.command.execute` by `keymap.dispatch(evt.data.command)` ([app](../../opencode/packages/tui/src/app.tsx), lines 1260–1263); the public keymap contract likewise exposes `dispatch(id)` and explicitly allows programmatic command dispatch ([SDK context declaration](../node_modules/@opencode/plugin/dist/tui/context.d.ts), lines 323–379). Thus **no authorization command, slash action, command-palette action or keymap callback may call the affirmative resolver**. Existing `opencode api`, `opencode service`, session/Form/Question/permission routes and a prior Implementer background process have no supported address for an unregistered Solid `onMouseUp` closure. The source-supported answer to questions C1–C9 is: direct local callback yes; server/session/Form/permission/command dispatch no; Orchestrator/Planner/slot/prior Implementer cannot affirm through their admitted OpenCode routes. This is the same lexical, client-local provenance principle as `ui.dialog.confirm`, with the event callback supplied by the plugin's small component instead of the built-in dialog. Form differs because its deferred is deliberately resolved by a public HTTP reply endpoint.

This is a source-path conclusion, not a claim of physical-human attestation or resistance to code injection into the trusted TUI. A plugin component that accidentally calls `context.keymap.dispatch` or accepts a client event as `Authorize` would invalidate it.

## 6. Candidate visibility and UX

The exact candidate is already a frozen object with `intent`, full `plan`, exact paths, canonical root, HEAD, encoding and digest ([proposal](../src/m1/proposal.ts), lines 5–18, 52–101). The complete human decision text comes from `candidateMessage(candidate)`. A non-modal projection should display that string without model echo or truncation. A bounded scroll area can make every line immediately inspectable while a fixed Authorize/Cancel row remains adjacent. “Visible” means available in that same scroll area, not every line simultaneously on a small terminal.

The composer slot is the preferred location because it stays part of the root session's normal view at widths where the panel becomes fullscreen. Its risk is vertical crowding. The wrapper needs an explicit usable-size condition, a scroll region, and controls that cannot remain active if the region loses enough height to inspect the plan. The panel gives a more comfortable split at wide widths, but its forced fullscreen transition and close-on-navigation make it a conditional alternative. Neither surface should present Authorize in a child session. Root → child while pending should settle STOP; child → root should show a settled STOP projection rather than resurrect the old decision. The same rule applies to another root/home/plugin route.

Use one pending resolver for one M2 attempt. The callback should compare the captured candidate/digest and active generation to the current activation-private pending decision, then atomically mark it settled before any asynchronous work. A replaced candidate must remove the old control and settle STOP; duplicate or stale clicks must be inert. Resize to an unreadable state, unmount, or ambiguous multiple projections must remove affirmative action and STOP. Text layout and mouse/key activation at the minimum acceptable terminal size are not proven solely by static source; §8 identifies the bounded check.

## 8. Runtime probe result or exact remaining probe

No runtime probe was run for this report. Source is sufficient to identify the direct local pointer callback and the absence of a supported server route to it; a live CAP request would add no useful security proof. **One bounded disposable UI probe remains before implementation planning** because static source does not settle the exact interaction quality or plugin JSX dependency loading on the installed CLI 2.0.18 with SDK 2.0.17.

Create a plugin/project only under `/tmp`, with any needed `solid-js`/OpenTUI peers there. In the actual installed TUI, show inert candidate-like multiline text in a `session.composer.top` slot, a capped scroll region, and local buttons whose callbacks only record `Authorize`/`Cancel` to disposable probe state. Verify: (1) the entire text can be scrolled and the action row stays associated at a normal and a narrow-but-supported terminal size; (2) a direct click invokes the local callback without a command registration, and a focused keyboard path can do so if keyboard parity is wanted; (3) root → child unmounts/disables it, child → root does not leave a stale active control, and reload cleanup prevents a stale callback; (4) resize below the readable minimum disables the positive control. Also observe that the panel becomes fullscreen at ≤80 columns if testing it as a fallback. Do not create or answer a real CAP request, run implementation agents, or touch the target worktree. The probe would prove rendering and event/lifecycle behavior of that disposable component only; it would not prove M2 binding or grant checks.

## 9. Recommended smallest architecture

Planner result → trusted freeze of one candidate → root composer-top slot renders the exact `candidateMessage` in a bounded scroll region with adjacent Authorize/Cancel controls → direct TUI-local callback settles a single activation-private decision → trusted liveness, candidate, transcript, root/HEAD and Git freshness rechecks → existing one-use CAP grant and same-child Implementer admission → existing Git scope gate → the same root slot shows PASS or STOP without decision controls.

Pending decision dismissal, root navigation away, component unmount, panel hide (if used), unreadable resize, candidate change, host shutdown and plugin deactivation all mean STOP. The plugin's cleanup first revokes its generation and settles the pending resolver as cancellation; a late old callback checks revocation and cannot authorize. `assertLive` already rejects work after generation revocation ([M1 attempt](../src/m1/attempt.ts), lines 6–33). Session/Planner/slot transcript changes and root/HEAD freshness changes remain the existing M2 post-decision checks ([M2 attempt](../src/m2/attempt.ts), lines 232–261). Cancel, duplicate clicks and late clicks cannot produce a second grant. On host shutdown there is no persisted authorization or recovery: the in-memory pending decision is gone.

After settlement, the controls disappear; a root-scoped PASS/STOP projection can remain for that TUI generation and be remounted after child → root navigation. It is UI memory, not conversation history or CAP authority, and disappears on TUI restart/reload. If the user closes a panel before settlement, STOP; after settlement, closing only hides the result. The present large modal remains a fallback if the actual slot cannot meet the readable-size requirement.

## 10. Likely implementation surface

Later authorized work would most likely touch [the TUI plugin](../.opencode/plugins/opencode-agents/tui.ts) for the activation-private decision and root projection, one small `.tsx` component under that plugin or `src/m2` for the bounded scroll and direct controls, and [the M2 attempt](../src/m2/attempt.ts) for awaiting that local decision and keeping its current rechecks. Existing [proposal formatting](../src/m1/proposal.ts) and [grant mechanics](../src/m1/attempt.ts) are reuse points. Package/configuration changes might be needed to make the optional Solid/OpenTUI peers importable. No such file was edited in this exploration.

## 11. Open blockers

- The single disposable runtime probe in §8 must establish JSX peer loading, scroll/control legibility, and direct event/focus behavior on the installed binary. If the composer slot cannot keep full content inspectable with the action row at a usable size, this recommendation must be revisited.
- The public panel has an established narrow-width fullscreen behavior, so it cannot satisfy the always-visible normal root view across all sizes without a fail-closed threshold. This is a known host limit, not an unresolved CAP callback route.
