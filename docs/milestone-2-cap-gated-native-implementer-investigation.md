# Milestone 2: CAP-gated native Implementer investigation

> **Current status:** The finding below remains valid: a direct
> model-originated `subagent("authorized_implementer", ...)` call cannot
> itself be the CAP admission under the current hooks and permission APIs.
> Candidate 1 does not require that call to carry CAP authority. The
> Orchestrator creates only a mechanically read-only `implementer_slot` child;
> after confirmation and freshness checks, trusted TUI code switches that
> same child, consumes the process-local grant, and submits the exact frozen
> proposal. See the [controlling threat-model reassessment](milestone-2-native-child-threat-model-reassessment.md).

## 1. Executive conclusion

**Classification: SUPPORTED WITH SMALL BOUNDED SEAM, for one fresh native child; not supported directly for one built-in `subagent("implementer", ...)` tool call.** On this OpenCode checkout the model's native `subagent` call is executed in the server. The active TUI plugin generation has no supported pre-execution callback into that call. Neither changing a session permission nor replying to a generic permission request binds the exact frozen proposal and consumes a TUI-private grant. Therefore **CAP cannot safely unlock one exact model-originated native Implementer invocation today**. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 100–218; `../opencode/packages/plugin/src/effect/tool.ts:ToolHooks` lines 20–51; `../opencode/packages/plugin/src/tui/context.ts:Context` lines 516–532.]

The smallest coherent host seam for the *required admission sequence* is to expose `parentID` on public `session.create`, with the server passing it to the existing internal `Session.create`. CAP can then keep `subagent:implementer` denied to the Orchestrator, create one fresh native Implementer child under that Orchestrator, consume its private grant before prompting the child with trusted frozen text, and bind returned child and prompt IDs as M1 does. This retains the native session family and child transcript. It does **not** produce an Orchestrator assistant `subagent` tool-call row or foreground tool result; those require a larger TUI-callable native-subagent operation or a TUI pre-tool gate. If literal model-originated `subagent(...)` invocation and its clickable parent tool row are mandatory, the `parentID` seam is insufficient and the next step is a minimal OpenCode host/API proposal for a TUI-generation-bound pre-tool gate. ## 2. Native `subagent` execution path

1. The Orchestrator's model receives a `subagent` tool definition, then emits arguments containing `agent`, `description`, `prompt`, optional `model`, optional `sessionID`, and optional `background`. The host runner publishes a tool call and forks each local tool execution into its own fiber; multiple calls can overlap. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Input` lines 29–48; `../opencode/packages/core/src/session/runner/step.ts:attempt` lines 83–129.]
2. `Tool.snapshot.execute` triggers server plugin `tool.execute.before` with parent session, agent, assistant message, call ID, and mutable input. It then executes the selected tool. The tool runtime validates the resulting input before calling its implementation. `tool.execute.after` sees the outcome and may alter the returned result, but is too late to prevent child creation or prompt admission. [Host: `../opencode/packages/core/src/tool.ts:beforeExecute,executeTool,Snapshot.execute` lines 103–155, 263–284; `../opencode/packages/core/src/tool/runtime.ts:execute` lines 28–68; `../opencode/packages/plugin/src/effect/tool.ts:ToolHooks` lines 20–51.]
3. The native subagent implementation resolves the target agent, rejects unknown/primary targets and excess nesting, then asserts permission with **action `subagent`, resource `[agent.id]`**, `save: [agent.id]`, parent session ID, parent agent, and source `{messageID,tool-call id}`. `planner` and `implementer` can be distinguished by resource. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 109–151; `../opencode/packages/core/src/permission.ts:evaluate` lines 87–96.]
4. The permission service reads the current parent session and agent rules on each assertion. It merges agent rules followed by session rules; the last matching rule wins. A configured `deny` blocks before saved allowances or the `permission.evaluate` server hook. An `ask` creates a pending server request and waits for a reply; an `allow` continues. [Host: `../opencode/packages/core/src/permission.ts:configured,evaluateInput,assert` lines 158–188, 231–263.]
5. After permission, `sessionID` continues an existing child (and may switch its agent/model); absent `sessionID`, the server creates a fresh session with `parentID: context.sessionID`, target agent and selected model. It prompts that child with a host sentence plus the **model-supplied** prompt, starts a subagent job, and either returns `{sessionID,status,output}` in foreground or a running child ID followed by synthetic parent notification in background. The tool result also carries child ID in metadata. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 153–265; `../opencode/packages/core/src/session/subagent-completion.ts:deliver` lines 20–44.]
6. The TUI's parent tool row navigates using that metadata; its session-family picker uses `parentID` and also navigates to a child. These are separate UI affordances. [Host: `../opencode/packages/tui/src/routes/session/index.tsx:Subagent` lines 3106–3138; `../opencode/packages/tui/src/routes/session/composer/subagents-tab.tsx:SubagentsTab` lines 36–59, 160–167.]

This is a native *execution* permission, not CAP authorization. A general permission decision grants only tool capability. M1 requires an exact candidate, affirmative trusted confirmation, fresh root/HEAD/cleanliness, and process-local one-use consumption. [Project: `docs/coding-authority-protocol.md:Authority lifetime,Intent authorization`; `src/m1/attempt.ts:grantIntent,consumeIntent,runM1` lines 21–33, 151–188.]

## 3. CAP gating mechanisms examined

### Dynamic permissions and a temporary allow

`session.update` accepts replacement `permissions`, and the server publishes `SessionEvent.Permissions`, projected into the session table. The TUI client can call this API for an existing parent session. Consequently rules **can change during a live parent session**, and a session rule can override an agent's `subagent:implementer` denial while leaving `subagent:planner` allowed. A tool snapshot is prepared for a model request, but the native subagent implementation performs its own permission assertion at execution time. [Host: `../opencode/packages/client/src/effect/api/api.ts:SessionUpdateInput` lines 250–257; `../opencode/packages/server/src/handlers/session.ts:session.update` lines 255–278; `../opencode/packages/core/src/session/session.ts:setPermissions` lines 83–89; `../opencode/packages/core/src/session/projector.ts:SessionEvent.Permissions` lines 584–590; `../opencode/packages/core/src/session/context.ts:select` lines 127–142; `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 138–151.]

That update is a **durable session-wide rule**, not a grant scoped to one tool-call ID, arguments, or TUI generation. No counter, consume, compare-and-swap, or automatic revert exists in the permission rule or update API. Two already emitted tool calls can run in separate fibers and both evaluate during an allow window. A call admitted before the subsequent deny can proceed after revocation; changing the rule later does not undo the earlier assertion. The model can also choose altered `prompt`, `sessionID`, `model`, or `background` during the window. Thus temporary allow is weaker than M1, even if trusted TUI code immediately restores deny after observing one child. [Host: `../opencode/packages/schema/src/permission.ts:Rule` lines 55–65; `../opencode/packages/core/src/permission.ts:assert` lines 231–263; `../opencode/packages/core/src/session/runner/step.ts:attempt` lines 83–129; `../opencode/packages/core/src/tool/plugin/subagent.ts:Input,Plugin` lines 29–48, 153–218.]

Static `subagent:planner = allow` and `subagent:implementer = deny` is a useful **defense boundary** for a trusted TUI launch route. Agent rules are loaded into the server's agent registry from configuration; session overrides live with the session and must be reviewed because they are evaluated after agent rules. Saved `always` permissions cannot override a configured deny in `evaluateInput`; conversely a mistakenly broad session allow can defeat the agent's denial. The Orchestrator must also lack shell or other model-callable routes to the server API or independent commands that launch Implementer; denying only `subagent` is not a complete role review. [Host: `../opencode/packages/core/src/config/plugin/agent.ts:Plugin` lines 84–123; `../opencode/packages/core/src/permission.ts:configured,evaluateInput` lines 158–188; `../opencode/packages/core/src/tool/plugin/opencode.ts:Plugin` lines 68–133; project: `docs/milestone-2-native-orchestrator-investigation.md:Selectable conversational main agent`.]

### Permission `ask`

`subagent:implementer = ask` pauses at `Permission.assert` before session creation. Its request contains action `subagent`, target resource `implementer`, parent session ID, and source message/call IDs; the native subagent assertion provides **no prompt, continuation ID, model, background value, proposal digest, or exact arguments in request metadata**. The TUI's built-in permission view may look up the associated assistant tool part to display input, but this is a separate, asynchronous UI read, not an atomic pre-execution argument-binding API. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 138–150; `../opencode/packages/schema/src/permission.ts:RequestFields,Source` lines 16–41; `../opencode/packages/tui/src/routes/session/permission.tsx:PermissionPrompt` lines 122–132; `../opencode/packages/tui/src/util/permission.ts:permissionPresentation` lines 75–83.]

The standard TUI permission prompt can reply `once`, `always`, or `reject`; `autoaccept` replies `once` without a CAP decision. Any client with the request ID can use the public permission reply endpoint. `once` resumes **that pending permission assertion** but does not validate or rewrite its tool arguments. A later `ask` is normally a new request. `always` saves a project-wide `subagent:implementer` allowance and can release other pending matching requests; it therefore creates a durable bypass if there is no configured deny. A configured deny never reaches `ask`. These mechanics make `ask` unsuitable as CAP's sole gate even if the TUI plugin itself tries to reply once after confirmation. The generic permission UI or autoaccept could independently admit an unapproved call. [Host: `../opencode/packages/tui/src/routes/session/permission.tsx:PermissionPrompt` lines 232–256; `../opencode/packages/tui/src/routes/session/index.tsx` lines 255–275; `../opencode/packages/server/src/handlers/permission.ts:session.permission.reply` lines 76–84; `../opencode/packages/core/src/permission.ts:reply,evaluateInput` lines 173–188, 265–319; `../opencode/packages/core/src/permission/saved.ts:add` lines 63–78.]

### Tool and permission hooks

The server **Effect plugin** API exposes `tool.execute.before` and `tool.execute.after`. Before execution, a server plugin can inspect the exact input and call IDs, reject by raising `Tool.Error`, or replace `event.input`; the runtime then validates and executes the replacement. After execution, it can observe or alter result metadata, including the native child's ID on success. A server `permission.evaluate` hook can set allow/deny/ask for a request, but the event has resource and source, **not exact subagent arguments**, and configured denial returns before that hook runs. Server `tool.transform` can add or wrap tools. [Host: `../opencode/packages/plugin/src/effect/tool.ts:ToolHooks,ToolFailures,ToolDomain` lines 20–59; `../opencode/packages/core/src/tool.ts:beforeExecute,executeTool,Snapshot.execute` lines 103–155, 263–284; `../opencode/packages/core/src/tool/runtime.ts:execute` lines 28–68; `../opencode/packages/plugin/src/effect/permission.ts:PermissionEvaluation` lines 7–24; `../opencode/packages/core/src/permission.ts:evaluateInput` lines 173–188.]

Those hooks run in the **server plugin runtime**, not in an installed TUI plugin activation. The public TUI plugin `Context` has `client`, `data`, and `ui`, but no `tool.hook`, `tool.transform`, or `permission.hook`. Making a server hook consume a CAP grant requires sending or reconstructing authority across processes and keeping it synchronized with TUI-generation cleanup. A model-supplied digest, session metadata, event, or persisted record does not solve that trust transfer. A new host-managed synchronous TUI pre-tool gate could solve it, but it is not a current API. [Host: `../opencode/packages/plugin/src/effect/plugin.ts:Context` lines 26–54; `../opencode/packages/plugin/src/tui/context.ts:Context` lines 516–532; `../opencode/packages/tui/src/plugin/context.tsx:createPluginContext,deactivate` lines 156–218; project: `docs/charter.md:CAP runtime` lines 65–69.]

### Custom narrow adapter tool

A zero-argument `start_authorized_implementation()` is attractive only if its executor can read the active TUI generation's private candidate and grant. Current custom tools are registered with the **server** `tool.transform` domain; their execute callback gets server tool context, not TUI `ui.dialog` or activation-private state. Server code could internally create a child using server session services, but that would move admission authority to the server or require a cross-process capability service. Returning a native child ID would not repair that trust issue. A server tool that accepts an attempt ID or `approved: true` from the model is forgeable. A TUI-only command is not a model-callable tool. Reject this adapter under the current API. [Host: `../opencode/packages/plugin/src/effect/tool.ts:ToolEditor,ToolDomain` lines 8–18, 54–59; `../opencode/packages/plugin/src/effect/plugin.ts:Context` lines 26–54; `../opencode/packages/plugin/src/tui/context.ts:Context` lines 516–532.]

### `session.command`

Trusted TUI code can call the public `session.command` endpoint with a chosen parent session and text. A configured `subagent` command creates a child with `parentID`, prompts it, and starts a background subagent job. This can yield native family navigation and later parent notification. However the public command response is `void`, so CAP does not receive the child ID or prompt ID atomically. The command is also in the general command registry and callable through the ordinary TUI slash-command path; it has no CAP-only invocation condition. Text substitution is derived from the caller's text and template, and there is no one-use CAP check in `Command.execute`. Searching events or child lists to infer identity would be correlation, not a returned binding, and does not remove independent command invocation. [Host: `../opencode/packages/client/src/effect/api/api.ts:SessionCommandInput,SessionCommandOutput` lines 281–291; `../opencode/packages/server/src/handlers/session.ts:session.command` lines 340–365; `../opencode/packages/core/src/session/command.ts:execute` lines 11–35; `../opencode/packages/core/src/config/plugin/command.ts:Plugin` lines 72–135; `../opencode/packages/core/src/command.ts:Interface,Command.execute` lines 42–48, 81–89; `../opencode/packages/tui/src/component/prompt/index.tsx` lines 1309–1323.]

## 4. Exact-input binding

One-call permission alone is insufficient. The native tool schema lets the model set `prompt`, `agent`, `description`, `model`, `sessionID`, and `background`; permission checks only target the resolved agent ID. A matching `implementer` permission can therefore admit a different plan or file set, a continuation of an existing child, or a call with an unsuitable model. The tool also prepends a host sentence to its prompt. A server `execute.before` hook could force `agent = implementer`, delete `sessionID`, `model`, and `background`, and replace `prompt` with the frozen CAP text before validation and execution—but this hook cannot directly read TUI-private CAP state today. A permission reply cannot rewrite any of these fields. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts:Input,Plugin` lines 29–48, 138–218; `../opencode/packages/core/src/tool.ts:Snapshot.execute` lines 263–284; `../opencode/packages/core/src/tool/runtime.ts:execute` lines 28–68.]

M1's trusted TUI code already constructs the Implementer prompt from the frozen `{intent,plan,files}` proposal, canonical root, and bound HEAD, then calls `session.prompt` itself. It checks the returned prompt ID, sole user input, final assistant role/result, and Git scope. With a public `parentID` create seam, that same pattern can send exact trusted input to a **new child** and bind its returned ID; no model-supplied Implementer arguments participate. The child is a normal OpenCode session, but its prompt path is not the built-in subagent tool. [Project: `src/m1/attempt.ts:implementerPrompt,completedText,runM1` lines 63–119, 175–194; host: `../opencode/packages/client/src/effect/api/api.ts:SessionPromptInput,SessionPromptOutput` lines 267–279; `../opencode/packages/core/src/session.ts:Session.create` lines 250–283.]

## 5. One-use and race analysis

| Case | Current model-originated `subagent` path | With `parentID` create seam and permanent model-side Implementer deny |
| --- | --- | --- |
| Before approval / forged approval prose | Static deny stops the call; any temporary allow or generic `ask` can bypass CAP. | Only TUI code owns create/prompt. Conversation claims create no grant. |
| Duplicate or concurrent calls | Runner forks tool calls; a temporary allow can admit both. `ask` creates separate requests and generic UI can answer either. | Parent `subagent:implementer` stays denied. CAP's synchronous consumed bit selects one TUI prompt. Second attempt fails before another prompt. |
| Reuse or replay | Session rule persists; saved `always` persists project-wide. A previously allowed `sessionID` can continue a child. | No model continuation is admitted. CAP never passes a grant to server/session state; ambiguous prompt failure spends the grant and stops. |
| Stale root/HEAD/candidate | Permission system has no Git or candidate binding. | Reuse M1 candidate integrity and immediate Git freshness checks before consumption; stop on mismatch. |
| Plugin reload | Updated session rule or saved permission outlives TUI activation; already admitted work continues. | Cleanup revokes old generation, and guards after awaits prevent a later CAP admission. Already submitted child work can continue; it carries no reusable grant. |

The right-hand column is a **design inference**, not runtime-proven behavior. It depends on retaining M1's synchronous generation-local `busy`/`consumed` guards, refusing continuation, verifying the selected parent and child IDs, and keeping effective Orchestrator `subagent:implementer` denied throughout. Existing M1 code consumes just before prompt and checks revocation after awaits. OpenCode's tool fibers and persisted session rules establish the unsafe temporary-allow race; no runtime probe is needed to establish that API-level deficiency. ## 7. Smallest viable design and architecture test

**Proposed with one host seam, not implemented:** expose `parentID` on `session.create`, retaining the internal existing-parent validation and mutually exclusive `location`/`parentID` contract. Configure the Orchestrator's effective permission to allow `subagent:planner` and deny `subagent:implementer`. Planner uses normal native `subagent` without CAP. Trusted TUI code binds its returned child/proposal to the parent attempt, freezes the exact candidate, confirms it, and checks freshness. CAP creates a one-use grant, creates `implementer` with `parentID = verified Orchestrator ID` and explicit role/model/permissions as needed, checks returned ID and freshness, consumes the grant synchronously, then sends exactly the frozen prompt via `session.prompt` and records the returned prompt ID. It waits and validates sole input/result and Git changed-path scope as M1 does. A failure or ambiguous API result stops the attempt; no retry. [Host: `../opencode/packages/core/src/session.ts:CreateInput,Session.create` lines 82–91, 250–283; `../opencode/packages/client/src/effect/api/api.ts:SessionCreateInput,SessionPromptInput` lines 199–209, 267–279; project: `src/m1/attempt.ts:runM1` lines 141–194.]

The required eleven-step test is met as follows: (1) native Planner proposal is bound to its child; (2) CAP freezes it; (3) trusted `ui.dialog.confirm` returns affirmative for that candidate; (4) root/HEAD/cleanliness are rechecked; (5) a private grant is created; (6) one new child is created under the verified parent; (7) the grant is consumed before its sole prompt; (8) TUI supplies exact frozen input; (9) returned child and prompt IDs bind result to attempt; (10) permanent model-side denial plus consumed/busy guards reject pre-approval, duplicate, stale, and continuation paths; (11) cleanup revokes the generation and late continuations check it. A child created but never prompted after failure is not an authorized implementation execution. An already admitted prompt may finish after reload, as in the current M1 process boundary, but it cannot authorize another admission. [Project: `.opencode/plugins/opencode-agents/tui.ts:setup` lines 4–37; `src/m1/attempt.ts:completedText,runM1` lines 95–198; `docs/coding-authority-protocol.md:Authority lifetime,Grant procedure` lines 47–64, 207–247.]

The native family picker and child transcript follow from `parentID`. The inline parent `subagent` tool row and foreground result do **not** follow from this seam, because no assistant tool call occurred. The Orchestrator may be informed of the result as untrusted narration, but that narration never grants Implementer admission. If the inline row is a hard M2 acceptance requirement, this minimal design does not satisfy that UX requirement. [Host: `../opencode/packages/tui/src/util/session.ts:sessionFamily` lines 9–42; `../opencode/packages/tui/src/routes/session/index.tsx:Subagent` lines 3106–3138; `../opencode/packages/core/src/tool/plugin/subagent.ts:Plugin` lines 252–265.]

## 9. Recommendation

**Next step: a minimal OpenCode host/API proposal for public `session.create(parentID)`, followed by M2 implementation planning only if native child family navigation without an inline parent tool row meets the M2 UX requirement.** This seam preserves M1's TUI-local authority and exactly-one Implementer admission. If the requirement is instead a literal CAP-gated built-in `subagent("implementer", ...)` model call, propose option 3 to OpenCode; current hooks, permissions, `ask`, custom tools, and commands do not expose that gate to a TUI generation. No runtime probe is needed to decide the present API question: the missing TUI callback/parent field, broad permission update, and missing exact arguments on permission requests are source-established. A later bounded UI probe could confirm the family-navigation experience of option 1 after an API change, but it cannot make the current API safe. Do not implement M2 or relax the CAP boundary on the strength of this report.
