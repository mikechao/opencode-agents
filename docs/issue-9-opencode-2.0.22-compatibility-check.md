# Issue #9: OpenCode 2.0.21 → 2.0.22 source compatibility check

Date: 2026-10-02. Scope: the completed minimal native CAP implementation and its actual host dependencies. This is a source compatibility check before the broader architecture review.

**Verdict:** no upgrade change requiring adaptation was identified in the inspected dependencies. The admission, sponsorship, native child, result, continuation, and TUI navigation paths remain supported by 2.0.22 source. Several unchanged dependencies rely on internal behavior. There is also a pre-existing ambiguity in what “malformed input” means: CAP checks the host-published input object; the host can recover incomplete provider JSON before publishing that object. This distinction needs resolution independently of the upgrade.

**This report does not validate live behavior on 2.0.22.** The 2.0.21 dogfood result is evidence for that version only.

## 3. Source-backed findings, by architectural significance

### 3.1 Admission sponsorship still reaches native policy without changing root authority

**Verified source behavior (A and B).** Activation order is internal pre plugins → external packages → internal post plugins: `A=B core/plugin/supervisor.ts:91–95 (resolve),138–169 (activate)`; actual loading is sequential in `A=B core/plugin.ts:139–146 (activate/load)`. `A=B core/plugin/internal.ts:213–247` puts input repair and the native Subagent plugin in pre; `249–267` puts ConfigAgent and Browser in post. Thus the server's external transform can wrap the built-in and create the sponsor before later config policy is applied.

`A=B core/state.ts:160–192 (State.create/get)` replays transforms in insertion order against fresh state. `A=B core/agent.ts:74–84 (editor.update)` creates a missing agent before invoking its updater; `109–114 (get/resolve)` reads the transformed registry. The public host adapter passes the update through and returns the final definition as `.data`: `A/B core/plugin/host.ts:121–154 (agent.get/transform)`. ConfigAgent appends global rules to existing agents and then appends configured agent rules: `A=B core/config/plugin/agent.ts:83–123 (Plugin transform)`. Browser appends `{action:"browser",resource:"*",effect:"deny"}` to every agent: `A=B packages/plugin-browser/src/connection.ts:26–28 (BrowserConnection.make)`. These establish the exact order assumed by P `native.ts:114–122`; the browser exception is concrete, not speculative.

Native `subagent.execute` resolves the target and calls `permission.assert` **before** child creation. Its assertion uses `context.agent` with the actual parent session, assistant-message, and call IDs: `A=B core/tool/plugin/subagent.ts:134–151,184–201`. Permission `configured` resolves an explicitly supplied actor in preference to `session.agent`, then appends session permissions: `A=B core/permission.ts:158–163`. `evaluate` uses the last matching rule (`87–96`); `evaluateInput` returns configured denies before saved allows or evaluate hooks (`173–188`); `assert` blocks/permits/asks at `231–247`.

P `native.ts:126–134` changes only the invocation actor and wraps/forwards progress. P `native.ts:54–55,113–124` rejects root session permissions and unsupported final sponsor changes before consumption. Its deny-only hook (`43–45`) narrows the sponsor's action/resource to one exact target, without setting an ask or deny to allow. The native assertion consequently selects sponsor permissions while parent ownership stays rooted in the Orchestrator. The child uses `input.agent`, not the sponsor, as its role.

The root's native tool remains discoverable: `A=B core/session/context.ts:130–139` snapshots merged agent/session rules; `A=B core/tool.ts:225–238,292–295 (snapshot/whollyDisabled)` disables a whole tool only when its final matching action rule is wildcard-resource deny. The root's later `subagent:planner=allow` keeps `subagent` in the catalog. Native target-description filtering (`A=B core/tool/plugin/subagent.ts:282–307`) hides denied/hidden targets from its appended available-agent list; it does not replace executor policy. #9 does not require Implementer to appear in that list.

**Assessment:** unchanged and supported. **Architectural inference:** the actor substitution is a working admission mechanism under these exact leaf-policy semantics, but it is not an explicit host CAP/delegation primitive. A host change tying actor to `session.agent`, moving permission evaluation outside the wrapped leaf, or altering transform precedence would matter even if the public context type stayed identical. Other trusted plugins and changing user policy remain part of the host trust boundary; this bounded comparison does not claim exclusive control over all permission hooks.

### 3.2 Exact published/decoded arguments remain enforceable; malformed bytes are a separate boundary

**Verified source behavior (A and B).** `A=B core/tool/plugin/subagent.ts:29–48 (Input)` requires three strings and permits only optional `model`, `sessionID`, and `background` fields; there are no decode transforms or defaults in this Struct. `100–108` registers canonical `subagent`, `codemode:false`, Input, Output, and the native executor. P `server.ts:18–20` updates that registration, and P `native.ts:204–223 (strictNativeInput)` preserves its schema-owned `makeEffect` validation while exposing detached Standard JSON Schema. The registered schema remains the same kind at B. `A=B schema/tool.ts:44,86–99 (ValueSchema/Result/Info)` nonetheless allows Effect codecs, Standard Schema, or JSON Schema generally; the public type alone would not prove the maker assumption.

Execution order is established through callers, not just the hook definition:

1. `A=B core/session/runner/step.ts:100–128` awaits `publisher.publish(tool-call)` before forking local execution.
2. `core/session/runner/publish-llm-event.ts:458–474` publishes `Tool.Called` with the original `asRecord(event.input)` in both A and B. `A=B core/bus.ts:395–435` applies durable projectors inside the committed transaction before returning; `A=B core/session/message-updater.ts:323–336` persists running input.
3. `core/session/model-request.ts` returns `Prepared.executeTool` delegating to the captured snapshot: **A:399–413, B:398–412**. Its diff concerns HTTP option composition, not tool execution.
4. `A=B core/tool.ts:263–281 (snapshot.execute)` triggers `execute.before` before effective-tool resolution/alias handling. `A=B core/plugin/hooks.ts:69–95` invokes callbacks sequentially in registration order and propagates the before hook's typed failure.
5. Earlier built-in hooks can repair input: `A=B core/plugin/tool-input-repair.ts:24–34,90–125 (repair)` handles strings/placeholders/closed-object extras; `A=B core/tool/plugin/subagent.ts:271–279` removes empty model/session fields. Then #9's before hook runs. Its `actualCall` compares the persisted original object as well as the hook input (P `native.ts:58–96`). Thus an earlier hook removing an empty optional key or extra field does not make the original call exact.
6. `A=B core/tool/runtime.ts:28–44,62–84,134–152 (execute/decodeInput/validateStandard)` validates after before hooks, then invokes the wrapped executor. P `native.ts:104–124` independently rechecks the decoded object before consumption. `Tool.execute` runs mutable after hooks and normalizes content only after execution (`A=B core/tool.ts:119–155`).

Invalid schema values that reach `tool-call`, unexpected tools, aliases, and input differences therefore reach CAP reservation/rejection or cannot pass `actualCall`. P `native.ts:85–96` reserves before its own awaited reads; losing reservations fail outside the owner's close-on-error block. This supports the bounded first-contender mechanism. It does not prove identical scheduling for every live multi-call stream.

There are **two different malformed-input paths**:

- A `tool-input-error` event publishes a failed tool part and does not call the executor/before hook: `A/B core/session/runner/publish-llm-event.ts:315–333,454–457`; `A=B core/session/runner/step.ts:116–117` only executes `tool-call`. Failed/streaming tool parts remain visible to P `native.ts:70–75`, which requires the admitted call to be the first post-control tool part. Such earlier evidence prevents later admission while it remains readable. Root settlement closes unused authority at P `native.ts:195–198`.
- The native provider helper can **recover incomplete local JSON into a tool-call**, rather than emit `tool-input-error`: `A=B ai/protocols/shared.ts:178–185 (parseToolInput)`; `A=B ai/protocols/utils/tool-stream.ts:1–7,72–106 (toolCall),206–245 (finish/finishWithInput/finishAll)`. On local parse failure it tries `partial-json.parse`, falling back to `{}`. `A=B ai/protocols/utils/partial-json.ts:37–57,282` accepts complete or incomplete JSON and attempts repair. A missing final object delimiter can therefore produce the same object as a complete call. This is pre-existing in A and B.

The original object inspected by CAP is the original **host-published object**, after provider parsing. It is not the original provider byte string. The projector replaces streaming raw input with `Tool.Called` input (`A=B core/session/message-updater.ts:317–335`); #9 checks that object, not the streamed JSON. Consequently, a recovered object containing exactly the authorized fields/values can satisfy #9 even if its incoming JSON was incomplete. No source change in this upgrade introduces that behavior.

**Assessment:** unchanged and supported for exact published/decoded argument admission. **Architectural inference/contract question:** the broad “malformed first contenders burn the claim” wording in P `docs/coding-authority-protocol.md:173–184` and the parser-failure comment at P `native.ts:70–71` must be interpreted at this object/event boundary. If the intended requirement is rejection of every malformed provider byte sequence, the current source does not establish that requirement on either version. Resolve its meaning before treating the broader architecture as satisfying it. This report proposes no fix or expanded provider policing.

### 3.3 Native child/result binding and the conservative output gate are unchanged

**Verified source behavior (A and B).** After permission assertion, the native executor creates a new child using actual parent ID, description, target role, and selected/inherited model (`A=B core/tool/plugin/subagent.ts:184–198`). `A=B core/session.ts:250–283 (create)` obtains the entire parent's location, including workspace identity, and inherits parent metadata and session permissions when not explicitly supplied. #9 requires empty root/child session permissions; agent policy is a separate registry concern.

The executor emits `{sessionID:child.id,status:"running"}` before prompt admission (`subagent.ts:200–213`), prefixes a new child's prompt with `You are a subagent spawned by another session.\n`, starts the native job, blocks the real parent, and handles interruption/error/cancellation/backgrounding (`220–256`). `A=B core/session/subagent-job.ts:37–52 (start)` resumes that child and finds the latest completed, non-error assistant; `A=B core/session/subagent-completion.ts:8–17 (text)` concatenates its text parts or supplies a no-text fallback. Completion returns declared output `{sessionID,status,output}`, content with the exact XML-like subagent wrapper, and metadata `{sessionID,status}` (`subagent.ts:252–265`). No #9 child scheduler, custom row, or direct prompt dispatcher is used.

P `native.ts:128–136` binds progress and freezes the original result via P `cap.ts:101–109`. P `native.ts:140–179` then checks successful idle root/child state, real parent, target role, location, child input and final assistant text, wrapper, native output, and persisted tool identity. The no-text fallback and background results are valid native behavior but do not pass this governed completed-text contract.

Normalization remains a separate step: `A=B core/tool/runtime.ts:45–59,109–131,259–266 (execute/encodeOutput/normalizeContent)` validates machine output and converts a string to one text item. `A=B core/tool.ts:140–155` permits after-hook mutations and normalizes them. `A=B core/session/runner/step.ts:121–125` then calls `ToolOutput.truncate` before publication. `A=B core/tool-output.ts:65–75,111–115` skips results that already carry a truncated marker, adds `truncated:false` to short results, and changes content/metadata for long results (defaults: 2,000 lines/50 KiB at `13–14`).

The publisher forwards final content and metadata to `Tool.Success`: **A `core/session/runner/publish-llm-event.ts:573–590`; B:581–598**. The offset is caused by a more detailed provider error message; the result path itself is unchanged. `A=B core/session/projector.ts:703–705` dispatches the event; `A=B core/session/message-updater.ts:342–355` persists original running input with terminal content/metadata, without reconstructing them from ephemeral progress. This validates the result-normalization comparison made by P `native.ts:176–179`.

**Assessment:** unchanged and supported for short, unmodified foreground results. **Architectural inference:** exact metadata equality and wrapper equality intentionally fail verification on truncation or an after hook that adds harmless fields. This protects against claiming transformed evidence as original success, but also couples authority verification to presentation details. It is an existing acceptance limit, not a 2.0.22 incompatibility. Root and child settlement plus fresh Git scope still determine trusted completion; native tool success alone is insufficient.

### 3.4 Synthetic publication/control admission and root settlement retain their sequencing

**Verified source behavior (A and B).** The plugin adapter forwards `session.synthetic`, `wait`, and `context` to Session: **A `core/plugin/host.ts:553–559`; B:562–568**. `A=B core/session.ts:374–376,428–449` maps context to projected history and synthetic/wait to the session handle. `A=B core/session/session.ts:274–312 (synthetic)` admits a typed inbox item before wake, defaults to steer, and suppresses wake for `resume:false`; an active revert also suppresses wake. P `attempt.ts:350–351` uses admit-only publication; P `native.ts:190–195` issues one exact steer/resume control and checks the admitted echo before waiting.

Inbox first-admission identity reconciliation is unchanged (`A=B core/session/inbox.ts:154–166`); #9 uses fresh IDs and still checks exact returned identity/text. At promotion, pending steers are ordered by enqueue sequence and published together up to a control boundary (`inbox.ts:458–487,496–509,533–548`). The earlier Plan publication and later CAP control can thus be delivered in that order on the same wake. `A=B core/session/projector.ts:609–638` consumes the pending row and inserts its exact synthetic ID/text/payload into projected history. `A=B core/session/runner/llm.ts:161–179,188–195` promotes before loading the next model context. `A=B core/session/runner/to-llm-message.ts:284–285` represents synthetic text as a user-role model message. The public delivery mechanism supplies instructions, not CAP authority.

`A=B core/session/run-coordinator.ts:93–110,136–145` records an execution before scheduling its drain and coalesces further wakes. Its `awaitIdle` follows successor executions and ignores their failure causes (`171–175`); `A=B core/session/session.ts:266–268 (wait)` delegates to it. Therefore wait alone is not a success assertion. P `native.ts:151–160` checks actual successful root/child outcomes after wait and P `native.ts:197` closes the claim on every outcome.

`session.context` uses `A=B core/session/store.ts:179 (SessionStore.context)` → `A=B core/session/history.ts:78–108 (messageEntries)` with latest-compaction selection and ascending sequence. It is a context window, not a guarantee of complete historical transcript visibility. #9's existing behavior is to fail closed when its exact control/call evidence is absent. The TUI's initial Planner verification separately reads paginated raw messages (P `attempt.ts:136–148`).

**Assessment:** unchanged and supported. **Architectural inference:** source establishes admission, promotion, and settlement ordering, not provider compliance with the exact proposed call or a single physical request. #9 deliberately assumes neither provider-request counting nor retry/compaction policing. A live check must still show that the installed 2.0.22 continuation produces the required readable control/call/result evidence.

### 3.5 Planner navigation still disposes the slot; retained authority remains outside its mount

**Verified source behavior (A and B).** `A=B tui/app.tsx:1367–1375` keys SessionFrame on `route.data.sessionID`. `A=B tui/component/session-frame.tsx:277–298` mounts Session inside that frame. `A=B tui/routes/session/index.tsx:1458–1474` mounts `session.composer.top` with the selected session ID and navigates a child Composer's close action to the parent. Native subagent-tab selection changes the route to the child's actual session ID (`A=B tui/routes/session/composer/subagents-tab.tsx:160–166,215–221`). `A=B tui/plugin/render.tsx:85–120,124–141 (Slot)` mounts contributions with component ownership and unregisters slot instances on cleanup. The same registered plugin contribution is recreated inside the new keyed route; normal Planner inspection therefore disposes the root DecisionStrip.

P `tui.tsx:35–46` owns retained/pending state in plugin setup, outside that mount. `238–251` invalidates frame proof at cleanup, retains pending Plan on route departure, and terminates on surface loss while root is still selected. Returning to root remounts a strip whose readiness is obtained from a new frame (`175–235`). Host JSX supporting that distinction is identical across the upgrade.

The public router adapter returns the actual store (`A=B tui/plugin/api.tsx:182–200 (ui.router.current)`); `A=B tui/context/route.tsx:33–43` uses a Solid store with `reconcile` on navigation. P `tui.tsx:77–80,359–363` reads route fields to subscribe; merely calling `current()` would not read those fields. Plugin context supplies the host renderer, client, location, and data (`A=B tui/plugin/api.tsx:136–144`).

The TUI data provider uses `createData` (`A=B tui/context/data.tsx:11–21`). Pending synthetic admission is deliberately visible in two projections: `A=B client/solid/data.ts:370–400 (admitLocal/materializeInboxMessage),773–782` materializes enqueue echoes; `1394–1437 (pending.list/sync/invalidate)` hydrates pending items and their visible messages; `1614–1647 (message.list/sync)` combines a reversed fetched window with pending/optimistic items. These establish P `attempt.ts:292–296`'s expected pending Plan and materialized synthetic message.

**Assessment:** unchanged and supported. **Architectural inference/live uncertainty:** Solid ownership supports the inferred disposal behavior, but renderer `frame` timing, mouse routing, clipping, width/height, and destroyed-node ancestry require the actual TUI. P `tui.tsx:196–216,227–234` depends on those values for readable-frame proof. None of the relevant TUI files or the host Solid patch changed between A and B.

The data source also reveals an existing limit: initial `message.sync` defaults to a 20-message window (`client/solid/data.ts:77,1625–1630`), while P `attempt.ts:295` compares the entire frozen parent history to the visible store plus Plan. Ordinary short Planner attempts fit; a longer initial root transcript may fail presentation coherence even when API history is complete. This is a conservative availability coupling, not new upgrade behavior or evidence of an authority bypass.
