# Issue #21 — Reviewer Native Launch Investigation

## Conclusion

Classification: **B**

Extend the existing trusted synthetic steer plus one-shot sponsored native `subagent` mechanism. After the accepted authorization RPC has proven Implementer settlement, native provenance, and HEAD/path scope, close implementation authority and issue one separate, predetermined Reviewer control input on the same Orchestrator root. Admit only its exact foreground `reviewer` invocation through a Reviewer-only sponsor, capture the native child identity, and independently verify settlement before publishing the terminal receipt and stopping before Commit. Keep the existing location-scoped exclusion throughout. OpenCode supports direct child session creation, but exposes no public dispatch API that also supplies the normal native subagent call publication, admission hooks, job lifecycle, and parent tool receipt relied on here. This path requires no new host launch seam or architecture decision; the subsequent #21 implementation can proceed on this basis.

Investigation basis: the clean local `../opencode` checkout reports `v2.0.22`, commit `527f0b931d1f9b3ebd34e106c51b31ce5db5b075`; both upstream package manifests report `2.0.22`. ## Current `opencode-agents` Launch Path

1. `src/attempt.ts` binds the native Planner result and publishes the retained Plan. `authorizePublishedAttempt()` verifies the published attempt and fresh Git evidence, transfers the explicit human decision, and calls `authorizeRpc.authorize` with `purpose: "implement"`, the frozen candidate, root/location, and publication identity. `src/authorize-rpc.ts` declares a host RPC, not a model tool; its origin remains within the existing host trust boundary.
2. `.opencode/plugins/opencode-agents/server.ts` creates `nativeAdmission(context)`, installs its hidden sponsor actor and `sponsorPermission` hook, composes `admission.before` with `models.before`, wraps the native `subagent` executor with `admission.execute(tool.execute, models.prepare)`, and registers the authorization handler.
3. `src/native.ts:authorize()` accepts one `NativeCap` claim per root. `src/cap.ts:NativeCap.accept()` occupies the slot before copying/validation; subsequent submissions cannot restore it. The server verifies the exact primary Orchestrator root, location, empty session permission overrides, and fresh Git baseline, then acquires the closure-local `executing` exclusion.
4. `nativeArguments()` and `controlText()` prescribe exactly `{ agent: "authorized_implementer", description, prompt }`. The server submits the unique `cap.control` through `context.session.synthetic({ delivery: "steer", resume: true })` and validates its admitted echo. Ordinary root permissions allow Planner delegation but deny Implementer, Reviewer, and Commit authority.
5. `before()` synchronously reserves the first contender using real root/message/tool IDs. `execute()` permits that executor to enter once. `actualCall()` binds the published original input to the exact synthetic control and first post-control tool contender, including parser-failed contenders. Exact keys exclude optional `sessionID`, `model`, and `background`, even when the host parser could normalize/drop them.
6. After `models.prepare()` and identity reads, a synchronous freshness/consume barrier spends the Implementer CAP. The wrapper invokes the captured native executor with the real parent/message/tool/progress context, changing only the permission actor to the narrow sponsor. It captures progress identity as `ChildBinding` (`unknown`, `exact`, or irreversibly `ambiguous`) and captures the original structured completion through `NativeCap.receipt()` before later host formatting/hooks.
7. `authorize()` waits for the root, then separately waits for the exact captured child. Root idle alone cannot settle a backgrounded child. `verifyResult()` checks root/child success, exact parent, role, location, empty permission overrides, fresh bootstrap input, child assistant identity/final completion, and the persisted completed parent call. It then calls `requireInScope(observeGit(...))`, proving unchanged authorized HEAD and permitted changed paths. Implementer prose does not establish success.
8. Today the RPC closes the CAP, publishes `receiptInput(..., outcome)` with `resume: false`, and releases exclusion only when settlement was proven. Unknown settlement retains exclusion until activation teardown. Its success receipt explicitly says Reviewer and Commit were not run.

The new transition belongs between step 7's successful trusted verification and step 8's terminal publication. It must not be triggered by detecting words in the returned success string.

## Direct Native Launch Assessment

**A is not the complete seam required here.** `context.session.create({ parentID: rootID, agent: "reviewer", ... })`, followed by `prompt` and `wait`, can directly create and run a linked native session with normal child history. The returned session ID allows exact identity observation; location inheritance and explicit model refs are supported. This path does not grant the child the Implementer's permissions.

However, direct session creation omits the native tool's subagent-mode/depth/admission checks, `Permission.assert` with a real tool source, native subagent job registration/blocking/cancellation coupling, progress publication, and structured parent tool receipt. Model precedence must also be supplied or resolved separately rather than coming through the native tool. Child tool permissions still apply during execution; the omitted boundary is the launch boundary, not all child permissions.

Alternatively, manually calling the executor obtained through `tool.list()` or a transform can run the built-in child/job code, but requires a supplied `Tool.Context`. The public API does not publish and dispatch a matching normal parent tool call for that context. It bypasses the normal before-hook/codec/after-hook/publisher chain, and the current admission wrapper rejects missing reservation/transcript evidence. Bypassing that wrapper or fabricating host events would redesign provenance. Neither direct alternative preserves the complete current native call semantics with a smaller change than B. Importing internal core services is not a supported plugin API solution.

## Synthetic Sponsored Launch Assessment

**B can preserve the required properties.** The server makes automatic review a mandatory continuation of *successful trusted verification*. The root model only proposes transport syntax; it never decides whether review is required, the target, or the admitted task. No successful terminal outcome may bypass the review branch.

Issue one unique Reviewer steer and create one closure-local admission slot bound to that control, the verified implementation, original root/location, and frozen three-key Reviewer arguments. Reserve the first contender synchronously; reject unexpected tools, wrong arguments, intervening inputs, reuse, optional keys, and duplicate executor entry. Spend admission before invoking the original native executor. A malformed owning contender or owner failure burns this attempt; no later proposal restores it. Losing contenders must not alter an in-flight owner's slot or settlement evidence. Parser failures must count when validating the published first contender, just as they do today.

Use a separate hidden Reviewer sponsor allowing only `subagent/reviewer`; retain the existing Implementer sponsor unchanged. Keep Orchestrator's configured Reviewer deny. The sponsor is passed only by trusted code after Reviewer admission and is never passed into the child session's permissions. Reviewer calls arriving without the exact pending slot must be rejected, including calls from children. Existing closed/consumed Implementer slots must remain unable to admit another Implementer.

Exactly once means one trusted launch attempt, at most one admitted native invocation, and exactly one fresh child on the successful path. A model refusal, malformed call, host deny, wake ambiguity, backgrounding, or unknown child identity can prevent successful review. Such cases end unverified; they cannot count as implementation-plus-review success and cannot trigger a replacement. The source cannot guarantee model compliance or eventual completion. That is a fail-closed failure condition, not a reason to add retries or a workflow engine.

## Recommended #21 Design

1. **Initiator and lifecycle:** Extend `nativeAdmission().authorize()` itself. Complete its existing root/Implementer waits and `verifyResult` evidence checks first. Represent successful verification as trusted data/control flow, retaining the authorized candidate and verified implementation target. Close the Implementer CAP before publishing Reviewer control. Do not expose review initiation through another model tool, ordinary RPC claim, Implementer output, or second human decision.
2. **One Reviewer admission:** Install one review-specific in-memory slot before the sole steer/resume submission. Bind its exact control ID/text, three-key arguments, root, location, and verified target. `before`/`execute` route this pending review explicitly before the existing CAP branch, because today's `caps.get(root)` remains present and would otherwise reject every new contender through a closed CAP. Outside that slot, Reviewer has no sponsorship. End/close the slot on every success, error, interruption, or admission ambiguity, without resetting it.
3. **Topology and agent:** Execute the original native tool with `agent: "reviewer"` in the trusted arguments and the unchanged root session ID in invocation context. Reviewer is a fresh root child, sibling to Planner and Implementer. Never attach it below Implementer or reuse a previous session. A role definition with subagent mode and read-only permissions is required; no Reviewer definition currently exists.
4. **Separate authority:** Give Reviewer its own narrow sponsor and trusted read-only tool restriction. Keep `NativeCap`, `purpose: "implement"`, the frozen human claim, implementation prompt, original clean-baseline freshness barrier, `consume`, and Implementer receipt semantics specific to implementation. Reviewer admission cannot issue authorization or commit authority, consume/reopen an implementation CAP, or sponsor another Implementer. Reject model tools outside its permitted observations, even if configured policy later appends allows.
5. **Identity and settlement:** Reuse small provenance checks for exact synthetic input, original published call, first contender, reservation IDs, native bootstrap, root/child role/location/permissions, progress/receipt reconciliation, and terminal session/history observation. Keep Reviewer control, reservation, child binding, and original structured result separate from Implementer's. Require completed native output/metadata and successful child evidence before accepting review. Settle the exact child independently of root idle, including on failure; an ambiguous binding is permanently ambiguous.
6. **Verification boundary:** Finish and retain implementation verification before the second steer. Today's `actualCall()` intentionally rejects later non-assistant/control input after its implementation control; rerunning that unbounded check after Reviewer steer would reject the new trusted control. Do not weaken that original admission check. Bind Reviewer to its own subsequent control segment and retain the implementation evidence already verified. The exact authorized change must remain the review target throughout; concrete fingerprint/result-format work is outside this launch investigation.
7. **Exclusion and receipt:** Keep the same location-scoped `executing` owner until Reviewer settles and trusted review verification finishes. Closing the CAP does not itself release that closure-local exclusion. Reset/recompute settlement evidence when Reviewer enters native execution: the old Implementer `settlementProven` must not release exclusion for an unknown/running Reviewer. Preserve identity capture before prompt admission, settle backgrounded/failed children, and retain exclusion on unknown settlement until teardown. This excludes competing managed implementations; it is not a lock against external editors or Git actors. Publish the accepted owner's terminal receipt once, with `resume: false`, only after the relevant root/child execution has settled. Stop before Commit.
8. **Model preferences:** Add `reviewer` to `src/agent-models.ts:managedRoles`. Existing `Role`, call validation, location/role storage keys, selection availability, `before()`, and `prepare()` then compose with the same execution path. Verify the original three-key call first; complete model/settings reads before spending Reviewer admission; inject an optional model only into the executor copy. Native model/variant validation and `override ?? agent.model ?? parent.model` remain unchanged. Missing preference uses native selection; malformed/unavailable preference fails without fallback or replacement.

No additional host completion callback or event-driven launcher is necessary. `authorize()` already awaits the full native execution and performs verification while owning exclusion. `src/attempt.ts:authorizePublishedAttempt()` keeps its transport/busy lifetime until that RPC returns. The TUI's `eventReceived()` ignores transferred ownership, so the Reviewer child does not need a second TUI authorization lifecycle; status text may need to describe the extended operation.

Avoid a generic worker manager or multi-purpose CAP. A review-specific local slot plus small shared evidence helpers is sufficient. Share pure checks or a bounded identity-observation helper only where both concrete paths need them; do not parameterize human authority, mutation permission, retries, or workflow phases by worker role. Neither source API nor topology requires that abstraction.
