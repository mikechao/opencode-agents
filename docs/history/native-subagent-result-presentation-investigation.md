## 2. Native subagent result lifecycle

1. The root model emits a local `subagent` tool call with a tool-call ID **T** in assistant message **A** in root session **R**. The host records its model-authored input under that ID before executing the tool ([step](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/step.ts), lines 100–129; [publisher](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/publish-llm-event.ts), lines 458–475). The required native input is `agent`, `description`, `prompt`; `model`, `sessionID`, and `background` are optional ([schema](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 29–48).
2. The tool resolves and authorizes the named agent, checks a supplied child belongs to **R**, or creates child session **S** with `parentID: R`, title `description`, selected agent and model. A new child receives the literal prefix `You are a subagent spawned by another session.\n` followed by `prompt`; a continued child receives `prompt` alone ([executor](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 134–218). It publishes running progress `{sessionID: S, status: "running"}`.
3. The subagent job resumes **S**, reads its messages, selects the newest completed, error-free assistant message among the last 20 returned, concatenates that message's text parts with `join("")`, and uses a fixed no-text sentinel if necessary. Call the resulting string **P**; in the current M2 success contract it is the Planner's sole final text ([job](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/subagent-job.ts), lines 36–52; [text extraction](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/subagent-completion.ts), lines 8–18; [M2 child verification](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m2/attempt.ts), lines 63–74 and 112–127). This extraction does not trim, reformat, or Markdown-render P. It does concatenate text parts and excludes reasoning and non-text content; M2 compares against that same concatenation.
4. In foreground success, the executor's internal output object is exactly `{sessionID: S, status: "completed", output: P}`. Its returned result has `output` equal to that object, `content` equal to **W(P)** = `<subagent sessionID="S" state="completed">\nP\n</subagent>`, and `metadata` equal to `{sessionID: S, status: "completed"}` ([executor](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 234–265). The internal object is schema-encoded, but the nonempty explicit `content` string is normalized to one text content item without altering its whitespace ([tool runtime](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/runtime.ts), lines 28–59 and 259–269). There is no child status, title, description, or separate completion summary inside W(P), apart from the `state="completed"` wrapper attribute. `description` remains recorded in the *input* and as the child session title.
5. Before publication, **every local tool result** passes the stock output limiter: default 2,000 lines or 50 KiB. Oversize output is replaced with a prefix plus a file-location marker; metadata gains `truncated: true` and `outputPath`. Under the limit, content is unchanged and metadata gains `truncated: false` ([step](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/step.ts), lines 117–125; [limiter](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool-output.ts), lines 13–15 and 65–115). Thus the host does **not** guarantee byte-for-byte P in the *stored parent result* for an arbitrary-length P. The current M2 exact wrapper comparison rejects a truncated or otherwise changed result before candidate creation ([`resultMatches`](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m2/attempt.ts), lines 129–136). In an accepted M2 bind, stored W(P) contains P exactly, including its original leading/trailing whitespace and newlines.
6. The local success event carries T, A, one nonempty text content item W(P), and metadata `{sessionID, status, truncated}`; the projector copies those fields into the completed tool part of A in canonical **root** history ([publisher](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/publish-llm-event.ts), lines 573–590; [updater](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/message-updater.ts), lines 340–358). The child's assistant text P remains in canonical **child** history. The structured internal output object is not separately persisted in this tool part; the wrapper and metadata are.
7. On parent continuation, the root model receives the completed tool result as a tool-role result tied to T: the single text content item becomes a text `ToolResultPart` whose value is W(P). Nonempty text tool history normalization leaves that value unchanged ([lowering](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/to-llm-message.ts), lines 125–139 and 208–229; [normalization](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/ai/src/tool-history.ts), lines 51–83). The root model sees S in W(P), and sees the original tool call input including `description`; it receives no extra host summary. This is ordinary later root model context, subject to the usual history/compaction boundary, not a visible assistant final.
8. The TUI projects A's tool part T as a root row. At default verbosity it dispatches `subagent` to the dedicated `Subagent` renderer; the child session remains independently navigable through S and `parentID` ([rows](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/rows.ts), lines 313–380; [dispatch](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/index.tsx), lines 2392–2460; [renderer](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/index.tsx), lines 3106–3138).

Root W(P) is durable tool-result data and later model context. Child P is durable assistant text. They are related by exact trusted comparison in M2; neither a root assistant text part nor a stock visible root plan block is created by that relation.

## 4. Native subagent options / modes

All six input keys in the native schema are model-visible: required `agent`, `description`, `prompt`; optional `model`, `sessionID`, `background` ([schema](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 29–48; [definition registration](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 100–108). `agent` selects the permitted child agent and appears in the row. `prompt` controls child input; it is not the completed result. `model` selects a child model and can add a model label to the row. `sessionID` resumes a child and changes the row to “Continue subagent”; it does not embed that child's answer. `background` returns a running status immediately and later sends the separate synthetic completion notice. A new child uses `description` as its session title and the root row's task label. `fork` and `parentID` are **not** input fields; the host sets `parentID` on creation and checks it on continuation ([executor](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 153–218; [row](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/index.tsx), lines 3106–3138).

`description` is a `Schema.String` with a model-facing instruction to be a short 3–5 word label, not a runtime length validator. A model could emit multiline text, but the renderer treats it as a label/session title, not as P. The call is authored before P exists; placing P there afterward would require a separate model copy or another call. There is no separate completion-summary argument, result/output/inline/parent-return/detail option, or result metadata override exposed by native `subagent`. The host returns completion metadata for IDs/status and the shared truncation metadata; the renderer ignores output text. Background completion is visible as a short description/status notice and is model-facing as synthetic text, but supplies no full root plan block ([background return](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 19–27 and 229–265; [notification](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/subagent-completion.ts), lines 20–44).

Current M2 intentionally uses only `agent`, `description`, and `prompt`, foreground, with new children; its exact argument check rejects other keys ([agent instruction](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/.opencode/agents/opencode-agents.md), lines 9–11; [binder](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m2/attempt.ts), lines 75–89). No unused native option improves presentation. A separately configured tool-output limit could change the maximum accepted result, but cannot make it visible in the native root row.

**NATIVE SUBAGENT OPTIONS DO NOT CHANGE THE RESULT-PRESENTATION LIMIT**

## 5. Planner output-format implications

The Planner currently returns one exact JSON object with `intent`, `plan`, and `files`; trusted `parseProposal` requires exactly that shape and validates paths ([Planner instruction](../../.opencode/agents/planner.md), lines 10–12; [parser](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m1/proposal.ts), lines 52–82). A Markdown-plus-fenced-JSON result, deterministic text with delimiters, or other format would require a corresponding exact trusted parser and unambiguous binding. It could make the **child** assistant transcript easier to read and would change the root model's W(P) context. It would **not** make the root `Subagent` row display any portion of P, because that renderer ignores output entirely. Nor would a longer `description` solve this: description is model-authored call input before P and is used only as a label/title. No output-format change alone meets root zero-click presentation; parse exactness must remain if the format ever changes for another reason.

## 6. Native result promotion / passthrough

Native foreground `subagent` returns a normal local tool result. The tool schema has an output object, explicit content, and metadata, with no “user-facing final” flag ([native tool](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 50–54 and 252–265; [tool result runtime](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/runtime.ts), lines 28–59). Local tool execution publishes `Tool.Success` to the parent assistant tool part, then the step determines continuation from the presence of a local tool call; the runner starts another model step when continuation is needed ([step](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/step.ts), lines 117–145 and 264–266; [continuation flag](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/publish-llm-event.ts), lines 608–618; [runner loop](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/llm.ts), lines 187–194 and 273–290). Neither native `subagent` nor this result/runner contract has return-direct, stop-after-tool, tool-only-final, child-takeover, or final-output-delegation semantics.

The parent tool result is lowered into a tool-role model message, not promoted into a root assistant `TextPart` ([lowering](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/to-llm-message.ts), lines 125–139 and 208–229). If a parent execution is externally stopped before normal continuation, the stored result remains a tool part and the user still sees the label, not an assistant final. A successful clean root turn with a visible final requires another parent model generation; its prose is a separate model-authored copy or acknowledgment. Current M2 requires exactly one successful parent turn and a nonempty final, but does **not** compare that final with P ([M2 parent checks](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m2/attempt.ts), lines 91–110).

The background mode is a different delivery mechanism: it initially returns running text, then a synthetic *user-role* item containing a wrapped child result, and may wake parent continuation ([completion delivery](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/subagent-completion.ts), lines 20–44; [synthetic lowering](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/to-llm-message.ts), lines 284–285). Its visible notice does not display P. It is neither direct-result promotion nor compatible with the current M2 foreground exact-call/whole-history shape.

**STOCK OPENCODE CANNOT PROMOTE SUBAGENT RESULT TO ROOT FINAL WITHOUT MODEL COPYING**

## 7. Child/session result surfaces

The supported path to read the full P visually is navigation to S: click the native row or select the child through the subagent picker. The child final assistant text is ordinary Markdown, persistent, and naturally scrollable in its own session. This is one row click at default verbosity; low verbosity may require expanding an activity group first. The parent remains navigable via its `parentID`, but is not simultaneously the active transcript ([native row](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/index.tsx), lines 3106–3138; [picker](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/composer/subagents-tab.tsx), lines 159–167 and 192–250; [parent action](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/tui/src/routes/session/index.tsx), lines 1286–1302). M2 dogfood directly observed native child navigation and final text visibility ([dogfood](milestone-2-live-dogfood.md), “Native child experience and result presentation”).

No stock hover preview, split child pane, child-result sidebar snippet, result footer, tool-detail drawer, or full-result completion toast was found in the matching TUI paths above. The background notice is a description/status line with navigation, and the root Copy/Export command can expose W(P) outside the active transcript. Neither offers exact P as a readable root plan next to the compact Authorize control. A plugin-owned panel could show a fetched result only through new project presentation code and a panel action; it is not a native subagent result surface.

## 8. Parent continuation semantics

For a successful, untruncated foreground call, the root model's tool context contains W(P) exactly. W(P)'s wrapper is fixed by the native executor and includes S and completed state. The original model-authored call contains `description`, `agent`, and `prompt`; the tool-result content adds no title or generated summary. The stored completed metadata includes S, completed status, and the shared limiter's truncation bit, but the ordinary text result supplied to the model is W(P) rather than the internal `{sessionID,status,output}` object ([native executor](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool/plugin/subagent.ts), lines 252–265; [limiter](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/tool-output.ts), lines 65–115; [lowering](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/to-llm-message.ts), lines 125–139). Provider transports encode that tool-result part into their protocol; no source path deliberately trims the nonempty W(P) text during host history lowering ([tool-history normalization](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/ai/src/tool-history.ts), lines 70–83).

The local call sets `needsContinuation`; the runner consequently asks the parent model to generate again, even if the child already supplied a complete answer. Tool choice `none` at an agent step limit may force a later text-only step, but does not turn the tool value into text. Suppressing or interrupting continuation leaves a tool row and no host-controlled tool-only final. The current root Orchestrator uses that later generation to call `implementer_slot` and then finish with informational prose. No separate parent model generation is needed to *store* W(P), but one is inherent to the normal parent turn after the call ([step and runner](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/step.ts), lines 264–266; [runner](https://github.com/anomalyco/opencode/blob/cd9a14a6b688d4021bee381dfd39d2cef9c0f862/packages/core/src/session/runner/llm.ts), lines 187–194 and 227–290; [agent instruction](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/.opencode/agents/opencode-agents.md), lines 9–11).

## 9. M2 binding implications

The existing strict native-result contract already has all relevant identities:

```text
root session R; one plain user message U (ID u); root history H0
→ parent Planner call in assistant message A₁, tool-call ID T₁
→ new Planner child S₁, input ID I₁, final assistant ID F₁, final text P
→ parent completed tool part T₁ stores W(P) and metadata.sessionID = S₁
→ native root row displays the call label and links to S₁; child view displays P
→ parent implementer_slot call in distinct assistant A₂, tool ID T₂,
  distinct child S₂, bootstrap final READY
→ root final in its own assistant step, then successful idle
→ trusted TUI bind verifies H0, both complete child histories, exact W(P),
  roles/IDs/prompts/status/idle, and fresh worktree/HEAD
→ parse P, freeze candidate C, request local authorization
```

The exact message/tool/child IDs are recorded in `Call`, `Child`, and `Bound`; `resultMatches` compares the entire W(P), and `bind` serializes the complete root and child histories for later equality checks ([types and checks](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m2/attempt.ts), lines 12–18 and 75–164). After authorization, the code rechecks root/Planner histories and the slot before consuming a process-local one-use grant and sending one exact trusted prompt to S₂ ([admission](https://github.com/mikechao/opencode-agents/blob/88739d991598b2c2818a484f98edb6e49d657407/src/m2/attempt.ts), lines 166–184 and 212–263). Any changed root/Planner/slot history, result mismatch, oversize truncation, or unexpected input must STOP. This binding proves data movement and identity, **not** that the TUI rendered P in the root. Since no viable native root display exists, only presentation remains unresolved. A future presentation source must be checked against the same frozen P/C and current histories; this investigation does not add one.

## 10. Threat analysis

Conversation and native tool rows have no CAP authority. The question is whether an actor can make the local strip authorize C while a different result is shown.

| Actor | Relevant ability and boundary |
| --- | --- |
| Root Orchestrator | Chooses native call arguments and later prose. It cannot make the dedicated row read another output field or cause native result promotion. Current M2 rejects extra/wrong calls, wrong prompts/child IDs, and changed root history. Prose is informational and must not be used as the authorization source. |
| Planner | Produces P; that is the allowed source for trusted parsing. It could write misleading prose inside its own final text, but exact P is compared with W(P), parsed under the strict proposal schema, and frozen as C. It cannot replace a displayed root native result because the native row displays no result. |
| `implementer_slot` | Read-only bootstrap must return exact `READY`; it cannot alter Planner P or admit implementation. Its distinct child/session/tool IDs and complete history are checked. |
| Prior or current shell-capable Implementer | Ordinary shell capability is within the accepted M1/M2 threat model, with known physical limits. It gains no CAP grant from conversation, child navigation, status, or stored W(P). A mutation to root/child history or relevant Git observations makes the trusted checks STOP; a direct local-client act is outside CAP admission and cannot be silently inferred as authorization. See the [controlling reassessment](milestone-2-native-child-threat-model-reassessment.md). |
| Stock host/TUI and trusted project TUI plugin | Trusted boundary. Host records W(P), enforces ordinary tool-result projection, and renders only the native label in root. Project TUI code owns the candidate, exact bindings, liveness/freshness checks, and the direct local authorization callback. A display-only surface cannot itself mint a grant. |
| Local human/client | May navigate, inspect child history, and explicitly use the local Authorize/Cancel callback. Merely opening S or reading a label is not approval. Manual re-prompting outside the governed attempt supplies no reusable CAP authority. |

There is no native root P presentation to substitute. If an implementation later presents P through a separate trusted UI surface, its exact visible content and active root/session identity must be bound to C before the local affirmative callback is enabled; the native W(P) comparison remains necessary. The compact strip itself should identify the frozen candidate, while all changing histories still fail closed.

## 11. UX comparison

| Surface | Exactness / persistence | Reading interaction | Fit with selected UX |
| --- | --- | --- | --- |
| Native returned subagent result | W(P) is canonical root history and later model context; exact for accepted M2 bounds. | Default root row shows label/link only. | Cannot provide zero-click readable root plan. |
| Native child navigation | P is canonical child assistant text, Markdown-rendered and persistent. | Click root row, read child, return to root; low verbosity may add a group click. | Good child inspection, but root and compact root strip are not simultaneously visible. |
| Composer-top fallback | Trusted TUI can render frozen C/P exactly from its process-local state; no model copy. | Zero-click root view with a readable bounded plan card; client-local display disappears on reload, and a new generation has no authority. | Stock-host fallback when full plan visibility is required. Existing M2 history/freshness binding remains the authority path. |
| Selected hybrid prototype target | Exact plan as naturally scrolling root conversation text plus compact composer-top local authorization. | Zero-click Markdown root plan and persistent conversation placement. | Not achievable from the stock native subagent renderer or native result promotion alone. The prototype's imported transcript was a visual simulation, not a production append mechanism ([decision](hybrid-authorization-ux-decision.md)). |

The native result is exact and root-owned **but hidden behind a label/navigation renderer**. The trusted composer-top plan is exact and zero-click **but client-local and outside the conversation scrollbox**. Those source facts are sufficient to accept composer-top as the stock-host fallback under the settled unmodified-host constraint; they do not imply that P must be copied by the root model. The current full-plan modal is known to block navigation and lose the result after dismissal ([dogfood](milestone-2-live-dogfood.md), “Native child experience and result presentation”).

## 12. Recommended stock-OpenCode direction

Use the already-verified native Planner result P as the data source and keep M2's exact W(P)/whole-history binding. Present the frozen candidate in a trusted, readable `session.composer.top` plan card in the **root** and place a compact Authorize/Cancel strip there with direct TUI-local callbacks. Keep native child navigation for deeper inspection. The control must bind the currently visible candidate, root R, P, HEAD/worktree and session histories before consuming the existing one-use grant. This works with unmodified stock OpenCode and requires neither native result promotion nor root model copying. It accepts that the full plan card is outside the root transcript, so it does not exactly reproduce the hybrid screenshot's scrolling assistant text. Do not reintroduce persisted attempt state or cross-process authority.

## 15. Open blockers / accepted compromise

- Stock OpenCode's native subagent result is durable in root history but intentionally rendered as a label/link there; no native option or result-promotion primitive supplies the selected zero-click scrolling root conversation block.
- A composer-top plan card is a client-local UI projection. After TUI reload or navigation it must not imply a surviving pending authorization; only the active trusted generation can offer its bound local callback. The plan's canonical P and W(P) remain available in child/root histories for later inspection.
- The shared tool-output limiter can truncate W(P). Existing M2 exact comparison already stops such a candidate; a future readable card must likewise refuse an incomplete result.
