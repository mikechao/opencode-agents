# Milestone 2 native-child threat-model reassessment

**Historical evidence.** This document records investigation, design, or observed behavior at an earlier repository state. It is not current normative documentation. See [`../README.md`](../README.md) for the current documentation map.

## 1. Executive conclusion

**CANDIDATE 1 IS CAP-COMPATIBLE.** The previous investigation applied a stronger post-run requirement to the switched child than accepted M1 applies to its editing-capable root Implementer. A persistent `authorized_implementer` selection is ordinary OpenCode role/tool capability, not a surviving CAP grant. With the narrow role and tool surface specified below, the Orchestrator's native continuation cannot use that selection to admit another mutation-capable turn: a call naming `authorized_implementer` is denied before child lookup; a call naming `implementer_slot` switches the child back before prompting. The trusted TUI can consume one process-local intent grant and submit one exact frozen implementation input to the exact child. Later direct local-client input is possible, exactly as for the M1 root session, and is outside that CAP admission. This is a source-based compatibility decision, **not** M2 implementation or runtime validation.

## 2. Actual V1/M1 threat model

**Normative architecture.** CAP authority exists only in the current trusted TUI plugin generation. Exact candidate freezing, `true` from the trusted confirmation invocation, binding and freshness checks create a purpose-bound process-local intent capability. Trusted process state consumes it **once when admitting one implementation attempt**. The frozen proposal is retained; the grant's usable bit is consumed. No agent, session, role, prompt, permission, saved approval, or durable record receives that capability. A later attempt needs a new candidate, current Git observations, and a new human decision. Revocation or death ends the generation's authority, while already started server/session work may continue without inheriting it. [CAP: `docs/coding-authority-protocol.md` lines 39–87, 205–247, 269–296; charter: `docs/charter.md` lines 61–69; orchestration: `docs/v1-orchestration.md` lines 237–247.]

**Implemented M1.** `grantIntent` creates `{digest, purpose, consumed:false}` only for an intact confirmed candidate. `consumeIntent` checks generation liveness, candidate identity/integrity, purpose, and unused state, then flips `consumed` before `session.prompt`. `runM1` creates an ordinary `general` root Implementer with editing/development capability, consumes the grant once, sends one trusted prompt, binds the returned input ID to the result, rejects unexpected extra inputs, and runs the trusted Git gate. TUI cleanup synchronously sets `generation.revoked`; awaited continuations check it. This is one **trusted admission**, not permanent revocation of that OpenCode session's editing tools. [`src/m1/attempt.ts` lines 6–33, 95–118, 161–194; `.opencode/plugins/opencode-agents/tui.ts` lines 4–37.]

**Answers to the M1 guarantee questions.** The consumed object is the private intent grant, not the proposal, role, session, or repository. After consumption the same grant cannot admit another implementation; the old confirmation cannot be rebound, replayed, recovered, or inherited. On generation death its grant and candidate/result binding disappear or are revoked for CAP use. M1 nowhere claims its root Implementer permanently loses edit capability. A local human/client can directly re-prompt that session using ordinary OpenCode input APIs; that is trusted-local OpenCode activity outside `/m1`, not reuse of CAP authority. Calling such activity a CAP-authorized later run would contradict the documents, which explicitly say generic OpenCode permission state is not authority and later CAP runs need fresh authorization. [CAP: `docs/coding-authority-protocol.md` lines 59–87, 269–296, 309–345; host: `../opencode/packages/client/src/effect/api/api.ts` lines 267–279.]

V1 trusts the installed OpenCode host/TUI, CAP integration, permission enforcement, and local OS/user-account boundary. It does not sandbox the local user or physically contain an Implementer with ordinary development shell access. CAP independently checks bound `HEAD` and ordinary Git-visible changed paths after the admitted attempt; it does not individually authorize each transient filesystem mutation, detect every concealed effect, or prevent deliberate child-process/shell tricks. Those limits apply to both root and child forms. [CAP: `docs/coding-authority-protocol.md` lines 89–118, 309–359; charter: `docs/charter.md` lines 65–89.] The [M1 live dogfood report](milestone-1-live-dogfood.md) is evidence of the root happy path, cancellation, and scope rejection, not of this unrun native-child sequence.

## 3. M1 root vs native-child comparison

| Dimension | Accepted M1 root after trusted prompt | Candidate 1 child after trusted prompt |
| --- | --- | --- |
| CAP authority | Private intent grant consumed; no second CAP admission. | Same consumed grant; no second CAP admission. |
| Role/tool capability | `general` with ordinary edit and development shell tools. | Stored `authorized_implementer` with ordinary edit and development shell tools. |
| Session state | Root persists and can accept later direct local input. | Native child and `parentID` persist; selected agent can remain `authorized_implementer` and accept later direct local input. |
| Local human/trusted client | Can manually re-prompt outside `/m1`; no CAP authority is inferred. | Can manually navigate to/re-prompt child outside CAP; no CAP authority is inferred. |
| Model-controlled parent | M1 has no model-callable parent continuation to this root. | Orchestrator has native child continuation, but only through its allowed target agent and with the source ordering proved below. |
| Trusted TUI | Has broad client APIs, but its CAP code submits only its grant-bound prompt and fails closed on ambiguity. | Same trust assumption; it additionally switches and verifies the exact child before submitting its grant-bound prompt. |

The extra native relationship is security relevant only if it lets the **model** reuse the editing role. Persistent state by itself does not do that. The prior report correctly established durable `switchAgent`, but its conclusion that direct promptability after generation death violates single use cannot be applied to Candidate 1 without also rejecting the accepted M1 root. ## 4. Orchestrator reuse analysis

**Native target check.** The native `subagent` input schema requires `agent`, `description`, and `prompt`; only `sessionID` is optional. For every call, the tool resolves `input.agent`, rejects a primary target, then asserts the **parent** `subagent:<resolved agent ID>` permission *before* fetching `input.sessionID`. Only afterward does it verify the existing child's `parentID`, switch an existing child to the named agent if different, and prompt it. Therefore `subagent(agent="authorized_implementer", sessionID=existingChild)` is denied before continuation or switching when that target is denied. Omission of `agent` fails schema decoding; a different allowed name is checked as that name and switches the child accordingly. The stored child agent cannot silently substitute for the required target argument. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts` lines 29–48, 134–218.]

For `subagent(agent="implementer_slot", sessionID=existingChild)`, the permission check allows the *slot* target, child identity is verified, `sessions.switchAgent` completes when the stored agent differs, **then** `sessions.prompt` admits the continuation. The runner selects the session's then-current agent at the context boundary and merges its agent rules with inherited session rules. Thus a resumed turn uses the read-only slot **if its effective merged rules remain read-only**. An interleaved trusted switch/parent continuation may cause an attempt to fail or run read-only; it does not grant the parent a mutation-capable continuation through this native call. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts` lines 138–218; `../opencode/packages/core/src/session/context.ts` lines 121–156; `../opencode/packages/core/src/session/runner/llm.ts` lines 162–178, 197–239.]

**Required role/configuration boundary.** The future Orchestrator must have an effective `subagent:planner=allow`, `subagent:implementer_slot=allow`, `subagent:authorized_implementer=deny`, and all-other-subagents deny policy; deny `edit`, `shell` (or any unrestricted shell), `execute`, and every installed mutation/session-control tool or MCP route. `execute` matters because Code Mode offers JavaScript `fetch` and composes exposed tools; it is not safe to leave it available merely because `edit` is denied. No model tool in the inspected built-in `opencode` namespace exposes `session.prompt`, `session.switchAgent`, `session.update({permissions})`, or `session.command`; its session rename/move tools are still inappropriate on the narrow Orchestrator surface. The TUI plugin's `context.client` is a trusted plugin API, not automatically a model tool. Any custom tool, server plugin, MCP tool, configured command exposed to the model, or shell route wrapping these APIs must be excluded. The future effective tool catalog and role plus inherited session rules must be checked; a session rule follows agent rules and the last matching rule wins. Child creation inherits the parent's session permissions, so a parent-wide session deny can also disable the authorized child, and a parent-wide allow can override a slot deny. Keep the narrow parent policy in its **agent** permissions or explicitly verify the child's resulting session permissions. [Host: `../opencode/packages/core/src/tool.ts` lines 225–284, 292–295; `../opencode/packages/core/src/codemode/tool.ts` lines 61–108; `../opencode/packages/core/src/codemode/web.ts` lines 13–40; `../opencode/packages/core/src/tool/plugin/opencode.ts` lines 82–145; `../opencode/packages/core/src/session.ts` lines 250–277; `../opencode/packages/core/src/permission.ts` lines 87–101, 158–188; `.opencode/plugins/opencode-agents/tui.ts` lines 4–37.]

This is a conditional source verdict about the specified future narrow surface. Those M2 roles and controls do **not** exist in this checkout; this report does not claim that the current repository already enforces them.

## 5. Child self-reuse analysis

For the ordinary native model/tool path, `authorized_implementer` must deny `subagent:*` (including itself and any equivalent mutation role), `execute`, and any direct or custom session prompt/synthetic/resume/command/switch/update tools. Default agent rules start with broad allow, so these denials must be explicit and checked against session overrides and the installed tool registry. The host's default native subagent depth of one also blocks a direct child spawning another subagent, but that configurable limit is not the boundary to rely on. Neither native `subagent` nor the inspected built-in `opencode` model tools provide a child self-prompt or self-switch route once these controls are removed. Ordinary repeated edit/tool calls within the single admitted implementation input remain allowed. [Host: `../opencode/packages/schema/src/agent.ts` lines 39–52; `../opencode/packages/core/src/tool/plugin/subagent.ts` lines 117–151; `../opencode/packages/core/src/tool/plugin/opencode.ts` lines 82–145; `../opencode/packages/core/src/session/context.ts` lines 127–142.]

**Physical shell limit, applied identically to M1.** An Implementer with ordinary shell access can in principle run a local OpenCode client/HTTP request if it obtains the local server credentials, start a child process, or use a background shell command. The host shell tool explicitly supports background jobs and posts a synthetic notification on completion, which can wake session execution. This means an absolute guarantee that an adversarial editing-capable model can never cause another model step or effect would require denying unrestricted `shell:*` as well as `execute`, all equivalent custom/network tools, and external process routes. Denying shell altogether would remove the ordinary development shell capability that M1 deliberately retains. V1 explicitly does **not** make that absolute guarantee for M1's root Implementer; its scope gate and behavioral instructions operate with these known limits. The minimum role denials above prevent a *native model-callable admission route*; they do not create a sandbox. M2 planning must retain M1's one trusted input/result binding, reject unexpected extra inputs, and stop without PASS on ambiguity. If the project later demands physical prevention of shell-mediated self-admission or background work, that would be a **new threat-model requirement for both M1 and M2**, not evidence that the switched child uniquely carries residual CAP authority. [Host: `../opencode/packages/core/src/tool/plugin/shell.ts` lines 116–151, 154–183, 188–265; `../opencode/packages/core/src/session/session.ts` lines 274–313; project: `src/m1/attempt.ts` lines 95–118, 177–194; CAP: `docs/coding-authority-protocol.md` lines 334–359.]

## 6. Generation-death analysis

After `switchAgent(child, authorized_implementer)`, grant consumption, and trusted `prompt(child, frozenProposal)`, an already admitted turn may finish if the TUI generation dies. The old generation is revoked and has no usable CAP grant. The Orchestrator cannot use the stored editing role through native continuation under its denied authorized target; its allowed slot target switches back first. The switched role is therefore ordinary durable session capability, not a route for the model to recover the consumed private grant. [CAP: `docs/coding-authority-protocol.md` lines 47–62, 81–87, 269–296; host: `../opencode/packages/core/src/tool/plugin/subagent.ts` lines 134–218.]

A local human/client may manually open and prompt that child, just as it may manually prompt M1's root Implementer. Both are trusted-local OpenCode actions outside the one governed CAP admission. A replacement `opencode-agents` generation must start with zero CAP authority and must never infer approval or a usable grant from the child ID, `parentID`, selected agent, transcript, prior prompt, or Git state. Its ability, as a trusted local client, to invoke ordinary OpenCode APIs manually is **not** reconstructed CAP authority. [Charter: `docs/charter.md` lines 36, 65–69; CAP: `docs/coding-authority-protocol.md` lines 269–296; host: `../opencode/packages/client/src/effect/api/api.ts` lines 238–279.]

## 7. Admission ordering

`session.switchAgent` publishes an agent-selection event that is projected to the persistent session row and an `agent-switched` history message. It does **not** itself call `prompt`, `synthetic`, `resume`, or `wake`. With an idle child and no pending input or external client action, the switch alone cannot run mutation tools. `session.prompt` admits an input and normally wakes execution; it has no per-prompt agent override. [Host: `../opencode/packages/core/src/session/session.ts` lines 90–96, 146–177; `../opencode/packages/core/src/session/projector.ts` lines 546–555; `../opencode/packages/core/src/session/message-updater.ts` lines 90–102; `../opencode/packages/client/src/effect/api/api.ts` lines 238–279.]

Smallest viable trusted sequence for M2 planning:

```text
freeze exact Planner proposal and candidate
→ trusted confirm returns true for that candidate
→ recheck candidate integrity, root, HEAD, ordinary cleanliness
→ reverify exact native child ID, parentID, bootstrap identity/result,
  expected slot agent, idle state, and absence of unexpected inputs
→ create one process-local candidate-bound grant
→ switch that exact child to authorized_implementer
→ after the awaited switch, assertLive and reverify child agent/identity;
  recheck freshness immediately before admission
→ assertLive; consume the exact grant once
→ assertLive; submit one trusted session.prompt to the exact child with
  the exact frozen proposal and bound baseline facts
→ retain returned prompt ID; wait and validate one admitted trusted input,
  selected agent, result, and no unexpected extra input
→ trusted bound-HEAD and ordinary Git changed-path scope gate; stop
```

The switch belongs **after** confirmation/freshness and grant creation, immediately before final verification and consumption; it is not itself consumption. `assertLive(generation)` is required after every awaited host/UI operation and immediately before grant creation, switching as an authority-bearing preparatory step, consumption, prompt submission, and final trusted Git decision. Do not restore the slot during an active authorized turn: the runner reselects the stored agent on later steps/retries, so restoration could alter the admitted attempt. Do not retry ambiguous submission. [Project: `src/m1/attempt.ts` lines 17–33, 82–118, 161–194; CAP: `docs/coding-authority-protocol.md` lines 47–57, 222–249; host: `../opencode/packages/core/src/session/runner/llm.ts` lines 162–178, 197–239.]

| Failure point | Repository mutation | CAP authority | Persistent OpenCode state |
| --- | --- | --- | --- |
| Switch succeeds; generation dies before prompt | Switch alone executes no model work; with an idle child, none from this sequence. | Grant dies/revokes; no CAP prompt admitted. | Child may retain editing role; direct trusted-local input remains possible. |
| Switch succeeds; final freshness fails | No model work from switch; stop without prompt. | Grant is unused but must be discarded, never rebound. | Editing role may persist; it is not an approval. |
| Prompt call fails unambiguously before admission | No admitted implementation input; stop. | Consumed grant is not reusable. | Editing role may persist. |
| Prompt result is ambiguous or TUI dies after submission | The exact input may already be admitted and may mutate/finish; no safe automatic retry. | Grant was consumed or revoked; no further CAP admission. | Editing role and any ordinary repository changes may persist. |

This analysis assumes the bootstrap child is idle and has no queued work when switched. Concurrent direct local input is trusted-local activity; an Orchestrator slot continuation can switch the agent back or add read-only input, making the governed attempt fail its result checks, but cannot obtain an authorized mutation turn through the native call. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts` lines 169–218; `../opencode/packages/core/src/session/session.ts` lines 146–177.]

## 8. UX consequence

Native `subagent` creates a session with `parentID` set to the Orchestrator, and its tool result records `metadata.sessionID`. The parent tool row uses that ID as its click target; session-family navigation follows `parentID`. Switching the child agent and directly prompting its existing ID do not replace that identity or relationship. Later user/assistant/tool messages remain in the same child transcript, including the authorized turn's normally exposed reasoning, tools, and output. These are source-established data/navigation paths; the exact mixed-turn presentation has **not** been live tested. [Host: `../opencode/packages/core/src/tool/plugin/subagent.ts` lines 184–218, 252–265; `../opencode/packages/core/src/session/projector.ts` lines 546–555; `../opencode/packages/tui/src/routes/session/index.tsx` lines 1827–1860, 3106–3138; `../opencode/packages/tui/src/util/session.ts` lines 9–43.]

The original Orchestrator tool row reports only the harmless bootstrap `implementer_slot` turn; it is not updated to represent the later trusted implementation result. That is a presentation mismatch, but not a material loss of the requested native relationship or child transcript visibility. M2 planning should label/report the later trusted result honestly rather than imply that the bootstrap row itself completed implementation. The preceding root-session UX observations and M1 dogfood are prior evidence only, not a runtime test of this candidate.

## 9. Final recommendation

**Proceed to M2 planning with Candidate 1.** Plan the narrow Orchestrator and read-only slot permissions, explicit authorized-child self-admission denials, exact child identity/result checks, TUI-local single consumption, and one trusted prompt/Git gate. Preserve the accepted M1 threat model and its ordinary-shell limitations. Do not implement M2 on the basis of this document alone, and do not rewrite the previous investigation.
