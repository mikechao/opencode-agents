# Milestone 2 native Orchestrator investigation

> **Current status:** The material host-gap conclusion below was an important
> intermediate result: the current TUI API cannot itself create and bind a
> native child, and a model-originated implementation-capable call is not a
> CAP admission. Later evidence established Candidate 1 using a native
> read-only `implementer_slot` bootstrap followed by trusted TUI switching and
> exact prompt admission of that same child. M2 no longer requires the TUI to
> initiate child creation or the Orchestrator to invoke
> `authorized_implementer` directly. See the [CAP-gated Implementer
> investigation](milestone-2-cap-gated-native-implementer-investigation.md)
> and the controlling [threat-model reassessment](milestone-2-native-child-threat-model-reassessment.md).

## 1. Executive conclusion

**MATERIAL HOST GAP for the full M2 flow on the selected OpenCode 2.x checkout.** Native primary agents, fresh child subagents, and navigable child sessions are supported. The missing supported operation is a TUI plugin generation initiating and binding a native child invocation from its private CAP control flow. The public `session.create` endpoint has no `parentID`; native child creation occurs inside the server's `subagent` tool or command implementation. The model can invoke that tool, but its invocation is model controlled and takes place outside the TUI CAP generation. The TUI generation cannot supply an unforgeable, one-use admission to that tool through the current public API. [Host: `packages/core/src/tool/plugin/subagent.ts:Plugin` (lines 100–264); `packages/core/src/session.ts:CreateInput` (82–91); `packages/server/src/handlers/session.ts:session.create` (124–138); `packages/client/src/effect/api/api.ts:SessionCreateInput` (199–209).]

The smallest **conceptual** M2 shape remains a selectable, read-oriented primary Orchestrator; native Planner and Implementer children; and the existing TUI generation owning proposal binding, confirmation, freshness, single use, and Git checks. It is **not yet an implementable recommendation** under the current host interface. A narrow host seam that lets the active trusted TUI generation request a native child with an atomic returned child ID and controlled prompt admission could make it viable. Adding a cross-process authority service or moving CAP into a server plugin would change the accepted V1 boundary. The recommended next task is **architecture reconsideration / host API design**, before M2 implementation planning. One bounded runtime probe below could settle only the command-path behavior, not remove the source-established admission gap.

## 2. Current M1 baseline

M1 is a live-dogfooded PASS for `/m1`: one fresh Planner root session, exact JSON proposal `{intent, plan, files}`, trusted candidate and TUI confirmation, immediate freshness recheck, one fresh Implementer root session, and an ordinary Git changed-path scope check, then STOP. The dogfood established a happy path, cancellation, and out-of-scope rejection; it explicitly did **not** establish native child delegation. [Project: `docs/charter.md:Milestone status and direction`; `docs/v1-orchestration.md:Current milestone boundary`; `docs/coding-authority-protocol.md:Milestone status and M2 boundary`; `docs/milestone-1-live-dogfood.md` lines 3–23, 63–129.]

The active TUI plugin keeps `{revoked,busy}` in activation-private closure state and revokes it synchronously on cleanup. `runM1` snapshots the selected TUI model once, observes the canonical Git root, HEAD, and cleanliness before Planner, creates a session with `agent: "general"`, `model`, and Planner edit denial, and records session and prompt IDs. It requires exactly one user input and one successful final assistant response from that session. It freezes a parsed exact-file proposal into a digest-bearing candidate, displays the whole candidate with `ui.dialog.confirm`, checks freshness, creates a distinct Implementer session, consumes a one-use intent grant before its exact frozen prompt, then independently observes HEAD and changed paths. [Project: `.opencode/plugins/opencode-agents/tui.ts:setup` (4–37); `src/m1/attempt.ts:completedText` (84–119), `runM1` (121–198); `src/m1/proposal.ts:parseProposal`, `makeCandidate`; `src/m1/git.ts:observeGit`, `requireFresh`, `requireInScope`; `test/m1.test.ts` focused cases.] The prior model finding is specific: newly created **root** sessions did not inherit the selected TUI model, so M1 now passes it explicitly. [Project: `docs/milestone-1-live-dogfood.md` lines 25–59.]

CAP authority is the active installed TUI plugin generation's private state. OpenCode sessions, role prose, model arguments, generic permission approvals, and native child visibility carry no authority. Ordinary failure ends the attempt; reload revokes the old generation, including late continuations. The role instructions and permissions are behavioral defense in depth, not containment against deliberate shell evasion. [Project: `docs/coding-authority-protocol.md` sections on authority lifetime, intent authorization, and M1 scope; `docs/cap-kernel-hosting-investigation.md:Executive conclusion` and `Candidate A`.]

## 3. `codex-agents` reference: the useful UX mechanism

The predecessor selected `orchestrator` by `default_agent` in `../codex-agents/opencode.json`; `../codex-agents/.opencode/agents/orchestrator.md` defines a `mode: primary` agent with read access, denied edits, constrained shell operations, and selected `subagent` permissions. `planner.md` defines `mode: subagent`, a configured model/variant, read access, and edit denial. The project config also sets `experimental.subagent_depth: 2`. [Reference: `../codex-agents/opencode.json:default_agent`, `:experimental.subagent_depth`; `../codex-agents/.opencode/agents/orchestrator.md` lines 1–70, 174–183; `../codex-agents/.opencode/agents/planner.md` lines 1–45.]

**Important historical distinction:** the current predecessor does not have its Orchestrator dispatch the Planner. Its configured built in **Plan** primary delegates planning to `planner`, presents and approves a persisted PlanArtifact, and hands an approved identity to the execution-only Orchestrator. The Orchestrator dispatches `implementer`, `code_reviewer`, and `committer` through its allowed native subagent tool. The predecessor's own documentation explicitly says Orchestrator is not the planning entry point. [Reference: `../codex-agents/opencode.json:agents.plan.system`, `:agents.plan.permissions`; `../codex-agents/.opencode/agents/orchestrator.md` lines 355–375; `../codex-agents/docs/opencode-orchestration-flow.md` lines 234–241, 435–436.]

The transferable UX technique is agent selection plus a model call to OpenCode's built in `subagent` tool. The tool constructs a new child with `parentID` equal to the calling session, prompts it with a self-contained task, waits by default, and returns its final text plus child session ID to the parent. OpenCode's TUI renders the parent tool call as a clickable child and lists family sessions; navigating to the child shows its own normal session messages. This is how the old Planner under Plan, and workers under Orchestrator, got a navigable native session rather than a custom activity panel. [Host: `packages/core/src/tool/plugin/subagent.ts:Input`, `:Plugin` lines 29–59, 184–264; `packages/tui/src/routes/session/index.tsx:Subagent` (3106–3138); `packages/tui/src/routes/session/composer/subagents-tab.tsx:SubagentsTab` (36–59, 160–167).] These are source-established mechanisms; this investigation did not rerun predecessor UX.

M2 should borrow only that native delegation/session presentation technique. The predecessor's Workflow MCP, durable PlanArtifact and Workflow state, operator descriptors, retry/repair, finding adjudication, continuation state, and compatibility logic solve its own larger workflow and do not supply M2 authority. [Reference: `../codex-agents/docs/opencode-orchestration-flow.md` sections on descriptor routing and workflows; `../codex-agents/.opencode/agents/orchestrator.md` lines 185–233.]

## 4. Current OpenCode source findings

### Selectable conversational main agent

Project `opencode.json` agent entries or `.opencode/agents/*.md` files define agent system text, description, model/variant, mode, and permissions. The Markdown loader maps its body to `system`; the `mode/modes` directory forces primary. `mode: primary` is excluded from subagent execution but is selectable in the TUI when not hidden; `mode: subagent` is omitted from the main agent picker. `default_agent` can select a configured primary. A selected main session is conversational and a normal user message is its prompt, so ordinary natural-language invocation needs no slash command. [Host: `packages/core/src/config/plugin/agent.ts:Plugin` (83–127), `:decode` (177–210); `packages/schema/src/agent.ts:Info` (22–54); `packages/core/src/agent.ts:selectedDefault` (92–129); `packages/tui/src/mini/footer.command.tsx:RunAgentSelectBody` (639–652).]

The Orchestrator can be given read/search permissions and `edit:*` and `shell:*` denial, with `subagent:planner` allowed and other subagent resources denied. Deny is a real OpenCode permission result, whereas `ask` permits user approval; neither is CAP approval. A broadly allowed shell, `execute`, custom tool, or project command can reopen mutation routes, so an Orchestrator permission review must cover its actual exposed tools. Denying `edit` alone does not contain shell mutation. Session permissions and selected agent permissions are merged; child sessions inherit parent **session** permissions/metadata unless overridden, while the child's **agent** permissions are evaluated separately. This makes role rules practical, but not an adversarial sandbox. [Host: `packages/core/src/permission.ts:configured`, `:evaluateInput` (158–188); `packages/core/src/session.ts:Session.create` (250–283); `packages/schema/src/agent.ts:Info.default` (39–53); project: `docs/charter.md` role restrictions.] Ordinary agents must have no reserved commit tool; obvious `git commit` shell forms should be denied, with the documented limitation of ordinary development shell access.

### Native child invocation and identity

The built in `subagent` tool takes `agent`, `description`, `prompt`, optional `model`, optional prior `sessionID`, and optional `background`. With **no** `sessionID`, it calls `sessions.create({parentID: context.sessionID, agent, model, title})`, yielding a distinct new session and fresh transcript. It prepends one host sentence to the exact model-supplied prompt and admits that text as the child's user input. Passing `sessionID` instead continues an existing child; M2 must prohibit/verify against this. It checks agent existence, rejects `mode: primary`, checks a nesting limit (default one child level), and asserts the parent agent's `subagent` permission for the target agent. It returns `{sessionID,status,output}` in foreground mode; a background job sends a synthetic result to the parent. Tool execution context contains parent session ID, agent, message ID, and tool-call ID, and the result metadata carries child session ID. These IDs identify an invocation for observation, but the model chooses when to call the tool and its inputs. [Host: `packages/core/src/tool/plugin/subagent.ts:Input`, `:Plugin` (29–59, 109–168, 184–264); `packages/plugin/src/effect/tool.ts:ToolHooks` (20–45); `packages/core/src/session/subagent-completion.ts:deliver` (20–44).]

Fresh child means new session history, not inherited parent conversation or hidden reasoning. The explicit `prompt` and the child agent's system instructions are the intended input. `Session.create` inherits location, metadata, and session permission rules; it does **not** copy parent messages. This inherited session permission detail matters: if the parent session has restrictive override rules, the Implementer could inherit them; if it has permissive overrides, the role design must check their interaction. [Host: `packages/core/src/session.ts:Session.create` (250–283); `packages/core/src/tool/plugin/subagent.ts` (184–218); `packages/core/src/permission.ts:configured` (158–163).]

Model order for a new native child is explicit `subagent.model` override, then child agent's configured model, then parent session model. The override accepts `providerID/modelID#variant` and validates availability. If no override is used and the role has no configured model, a parent session with the selected TUI model can pass that reference to the child. This is simpler than M1's root-session workaround, but the parent session's actual model/variant must be checked, not inferred from a global TUI selection; changed selection and variant behavior need an explicit M2 policy. Recommended policy if a host seam becomes available: snapshot the Orchestrator session's selected model/variant for the attempt and explicitly set the same reference on both children, unless a documented role-specific model is desired. No fallback or routing machinery is needed. [Host: `packages/core/src/tool/plugin/subagent.ts:resolveModel` (75–98), `:Plugin` (168–193); `packages/core/src/session/runner/model.ts:resolve` (88–104); project: `src/m1/attempt.ts` (127–145, 177–179).]

### Native TUI observability

The parent `subagent` tool part is clickable and navigates to its child session ID. The subagent picker builds the session family from `parentID`, shows each child agent/title/status, and navigates to a selected entry. A child exposes a `session.parent` command returning to the parent. Its ordinary transcript renders text, exposed reasoning parts, and tool parts; reasoning is collapsed in the default hide mode but can be expanded/toggled. The assistant footer shows role name and model name; an explicit tool model override is shown on the parent subagent row. The TUI can display only reasoning actually emitted by the model/host; it has no private hidden chain-of-thought reconstruction. [Host: `packages/tui/src/routes/session/index.tsx` lines 235–246, 1031–1045, 1269–1301, 1827–1861, 1865–1903, 3106–3151; `packages/tui/src/routes/session/message-parts.tsx:ReasoningPart` (42–105); `packages/tui/src/routes/session/composer/subagents-tab.tsx:SubagentsTab` (36–59, 160–167).] Native UI meets the visibility requirement for children created by the native path; no custom activity panel is indicated.

## 5. Candidate interaction and ownership shapes

The desired operator flow, conditional on a trusted child-admission seam, is: select `opencode-agents` primary; send an ordinary request; see a fresh Planner child; inspect its native session; see the TUI generation's frozen proposal and explicitly confirm; see a distinct fresh Implementer child receiving only that proposal; inspect it; receive the existing Git scope PASS/STOP. The Orchestrator's conversation may explain progress, but its prose never admits implementation.

| Shape | Host support | Trust assessment |
| --- | --- | --- |
| **A. Model → built in `subagent` → Planner/Implementer** | Fully native parent/child UX; foreground output returns to model. | Planner request, count, prompt, optional continuation ID, and Implementer dispatch are model-controlled. A model-visible approval statement or tool permission is not the TUI generation's CAP grant. If Orchestrator can invoke Implementer, it can invoke it before confirmation. If it cannot, the approved flow cannot invoke it. |
| **B. Model → narrow trusted request tool → server code → native child** | A server plugin can expose tools and access session services; its tool context gives parent/message/call IDs. | A request-only tool may signal the TUI, but it cannot own/consume TUI-private authority. Server code cannot receive the CAP confirmation result as a trusted host primitive. Making it the Implementer admission owner requires a new cross-process authority protocol. |
| **C. TUI plugin → native child under Orchestrator** | Internal `Session.create` supports `parentID`; the public TUI client `session.create` does not. | This is the right ownership for CAP, but lacks a supported atomic child create/prompt/result API from TUI. Existing `/m1` creates root sessions precisely through the public endpoint. |

One adjacent native route is `session.command`: a configured command with `subagent` creates a child under the supplied parent and starts it as a background job. The public command operation returns `void`, not the child ID; its command definition is also an independently callable session operation rather than a CAP-gated admission primitive. It is therefore not a clean Implementer bridge as exposed. Comparing child lists or event timing to infer an ID is weaker than an atomic returned identity, and independently invoking the command could bypass the TUI grant. [Host: `packages/core/src/config/plugin/command.ts:Plugin` (72–135); `packages/client/src/effect/api/api.ts:SessionCommandInput/Output` (281–291); `packages/core/src/session/command.ts:execute` (11–35).]

The TUI plugin can read the current route, selected model, session data, and events, and can show `ui.dialog.confirm`; these are adequate for observation and local CAP state but do not extend the public child-creation endpoint. Server plugin contexts lack that TUI dialog and can outlive the TUI generation. Generic RPC/events carry requests and artifacts, not a trusted proof of a particular TUI confirmation. [Host: `packages/plugin/src/tui/context.ts:Data`, `:UI`, `:Context` (63–85, 462–532); project: `docs/cap-kernel-hosting-investigation.md:Server plugins, MCP, and process boundaries`.]

## 6. Trust-boundary mapping

| M1 property | Native M2 evidence and required boundary |
| --- | --- |
| Fresh Planner context and identity | A `subagent` call without `sessionID` creates a fresh child and returns child ID. A trusted owner must bind that ID to one expected parent request and verify the sole prompt/result; the model's claim of freshness is insufficient. |
| Exactly one expected Planner request/result | M1 owns create/prompt IDs and checks history. Native tool checks neither M1's one-call policy nor exact source request. TUI verification of child transcript could reject extras, but a trusted launch/bind step is still needed. |
| Explicit proposal and candidate | Child output remains untrusted JSON. Keep `parseProposal`, exact paths, `makeCandidate`, and frozen digest in the TUI generation. Never use Orchestrator's paraphrase. |
| Human confirmation and freshness | Keep `ui.dialog.confirm`, canonical root, HEAD, cleanliness, post-Planner and pre-admission freshness checks, grant creation, and revocation in the active TUI generation. Native session visibility contributes no authority. |
| Exactly one fresh Implementer admission | M1 consumes its private grant immediately before the sole prompt. Native model dispatch lacks a trusted admission gate, and public TUI APIs lack native child creation. **Material gap.** |
| Distinct invocation and exact frozen input | A trusted launch seam should create a new child ID unequal to Planner's and send only the frozen candidate proposal plus bounded root/HEAD instructions. Model-composed `subagent.prompt` could alter scope or include Planner conversation. Verify child prompt ID and history as M1 does. |
| Context separation | A newly created child has no copied Planner transcript. The TUI must construct the Implementer prompt from the frozen artifact, not ask the parent model to relay it. Child location/session permissions are inherited, so review the effective role permissions. |
| Role permissions and no commit | Configure Planner edit denial, Implementer ordinary edit/shell allowance with exact-scope instructions, and obvious commit denial. Check effective agent plus inherited session permissions. These are OpenCode controls, not a shell sandbox. |
| Post-implementation evidence | Keep trusted TUI `observeGit`, bound root/HEAD, and `requireInScope` with exact authorized paths. Child final text or OpenCode tool summaries are not Git evidence. |
| Ordinary failure and generation revocation | TUI code must stop on denial, extra input, role failure, stale state, or scope failure, and recheck `revoked` after awaits. An already running server child may finish after TUI revocation, but has no CAP authority; its edits become current Git reality for a later attempt. |

The current implementation and normative documents support these obligations: [Project: `src/m1/attempt.ts` lines 17–33, 84–198; `src/m1/proposal.ts:parseProposal`, `:makeCandidate`; `src/m1/git.ts:observeGit`, `:requireFresh`, `:requireInScope`; `docs/v1-orchestration.md` sections 2–3; `docs/coding-authority-protocol.md` sections on intent and M1 scope.]

## 7. Simplicity assessment

M2 needs no Reviewer, Commit, new CAP kind, custom child UI, workflow engine, persisted phase state, general event bus, retry/repair, continuation, scope amendment, parallel roles, finding adjudication, or predecessor protocol compatibility. Native child UX already covers presentation. Role-to-role continuity should consist of the exact frozen proposal and trusted identifiers only. `/m1` remains the known-good harness until a later implementation explicitly replaces the intended UX. [Project: `docs/charter.md`; `docs/v1-orchestration.md`; reference: `../codex-agents/docs/opencode-orchestration-flow.md`.]

The conflict is narrow and concrete: native subagent creation is in the server, while authorization and immediate one-use admission are in the TUI activation. A server-side hook that accepts `approved: true`, a persisted grant, a saved OpenCode permission, or an Orchestrator message would weaken M1. A cross-process authority service is disproportionate to the M2 experience goal and was explicitly rejected for V1. A host-supported TUI-to-native-child operation could resolve the gap without moving CAP state, but that is a host capability proposal, not something established by the current public API.

## 8. Remaining uncertainty and bounded probe

No runtime probe can establish the missing public `parentID` field or make a model-controlled Implementer tool call into TUI-private CAP consumption; those are source-established design gaps. One **optional**, bounded probe is justified only if considering `session.command` as a host workaround:

* **Question:** In the selected OpenCode runtime, can a TUI plugin's call to a configured `subagent` command be bound unambiguously to one new child ID, exact child prompt, and parent result, while the Orchestrator session is live? Source shows a `void` response and background creation, but not the event timing and observable correlation under concurrent UI activity.
* **Minimal temporary surface:** a disposable local agent and command definition plus a disposable TUI probe that invokes the command in a scratch worktree with a read-only child, records returned/event/session identities, and presents no CAP grant. Do not alter M1 or permit edits.
* **Success evidence:** one new `parentID` child with the exact expected prompt and observable final result, uniquely correlated to the one command call even during a concurrent unrelated child creation. **Failure evidence:** no atomic or unambiguous identity/prompt binding, unexpected parent behavior, or independently invocable bypass.
* **Afterward:** remove the temporary definitions, probe plugin, and scratch worktree. Even a successful result would require an architecture decision about the command's independent invocation and lack of CAP-gated admission before using it for Implementer.

No probe was implemented or run here. The predecessor's native navigation is source-established; M1's own live dogfood did not exercise it.

## 9. Recommended next step

**Architecture reconsideration / narrowly scoped host API design.** Determine whether OpenCode will expose a supported atomic native child create/prompt operation to a trusted TUI plugin, with returned child and prompt IDs and a clear role/model/permission contract. If that seam is acceptable, plan M2 around one TUI-owned attempt retaining the exact M1 CAP and Git code, plus project primary/subagent definitions and native TUI presentation. If the host seam is unavailable, keep `/m1` as the known-good path and do not trade away its admission boundary for native session UX. The optional command probe may inform the host API discussion but is not an M2 implementation gate by itself.
