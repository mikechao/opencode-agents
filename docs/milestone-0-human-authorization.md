# Milestone 0 — Exact Human Authorization

## Status

Architecture proof / falsification milestone.

No production Coding Authority Protocol implementation should depend on a human-authorization mechanism until this milestone establishes that the mechanism is trustworthy enough to carry authority.

## 1. Objective

Determine whether an OpenCode-native interaction can provide a mechanically trustworthy, single-use human authorization bound to one exact kernel-generated candidate.

The required property is:

> A human explicitly authorizes one exact candidate produced by trusted code, and the authority kernel can distinguish that action from model output, generic permission state, automatic approval, programmatic replay, or unrelated session activity.

This milestone is not intended to build the Coding Authority Protocol.

It exists to prove or falsify one architectural dependency before surrounding infrastructure is created.

## 2. Why This Is Milestone 0

The proposed `opencode-agents` architecture depends on two distinct human authority boundaries:

1. approval of the exact intent and repository scope before implementation;
2. approval of the exact reviewed target before commit.

Neither authority may be inferred from:

* conversation text;
* an agent saying that the user approved something;
* prior approval of a related operation;
* an OpenCode permission that happens to allow a tool;
* a previous run;
* an earlier review;
* an automatically accepted interaction.

If OpenCode cannot expose a sufficiently trustworthy human-originated action, the proposed small OpenCode-plugin → authority-kernel architecture may need to change.

That question should be answered before designing durable workflow records, validation infrastructure, Git receipts, agent contracts, or broader protocol APIs.

## 3. Required Authorization Property

An authorization begins with an immutable candidate generated by trusted code.

Conceptually:

```text
candidate
  identity
  kind
  exact authority-bearing contents
  canonical digest
```

The candidate may represent different future authority boundaries, including:

```text
IntentAuthorizationCandidate
CommitAuthorizationCandidate
```

These names are conceptual only. This milestone does not establish production domain types.

The human must be presented with the meaningful contents represented by the candidate and must take an explicit action to approve or reject it.

A successful mechanism must establish all of the following properties.

### 3.1 Exact binding

Approval applies to one exact candidate.

Changing any authority-bearing input must produce a different candidate/digest and require a new human action.

Approval of candidate A must never authorize candidate B merely because they are similar.

### 3.2 Human provenance

Trusted code must have evidence that the approval resulted from the intended human interaction.

A model must not be able to manufacture equivalent evidence by:

* returning a special string;
* invoking another tool;
* emitting an expected payload;
* submitting a remembered token;
* replaying conversation content;
* generating synthetic user text.

### 3.3 Single consumption

An approval may satisfy its authority gate once.

After successful consumption, repeating the same callback, reference, event, command, or message must not create new authority.

### 3.4 Replay resistance

Previously observed approval material must not authorize:

* another candidate;
* another run;
* another commit;
* another session;
* a later invocation of the same operation.

### 3.5 No implicit authorization

The following must not independently satisfy the Coding Authority gate:

* OpenCode `allow`;
* OpenCode `always`;
* an existing permission rule;
* an automatic permission mode;
* lack of a denial;
* successful tool execution;
* an agent or prompt claiming approval.

OpenCode permissions remain useful defense in depth but are distinct from Coding Authority.

### 3.6 Failure is non-authorizing

Rejecting, dismissing, interrupting, timing out, closing, crashing, or otherwise failing to complete the trusted interaction must create no authorization fact.

Ambiguity must fail closed.

## 4. Trust Boundary Under Test

Milestone 0 should assume as little as possible.

### Potentially trusted

Only after experimentally establishing the relevant behavior:

* plugin code executing inside the supported OpenCode host;
* host-injected caller/session information;
* a specific OpenCode human-interaction primitive;
* the authority code that creates and consumes pending candidates;
* durable state required to enforce single consumption.

### Not trusted as authority

Regardless of convenience:

* model output;
* agent prompts;
* chat transcript;
* user text quoted or forwarded by a model;
* caller-supplied authorization claims;
* generic OpenCode permission state;
* previous workflow/run records;
* prior approval of another candidate.

The proof should minimize the number of OpenCode behaviors that the authority mechanism must trust.

## 5. Candidate OpenCode Seams

Milestone 0 should investigate available OpenCode-native mechanisms without assuming that any are sufficient.

Likely candidates include:

* plugin-owned TUI interaction such as a confirmation/dialog;
* native permission interaction tied to a specific resource/request;
* user-input or session events with host-provided provenance;
* another OpenCode-native primitive discovered during investigation.

Each mechanism must be evaluated against the required authorization properties.

The existence of a visible confirmation UI is not itself proof.

Likewise, a callback occurring after a user-visible interaction is insufficient unless caller provenance, exact candidate binding, replay behavior, and bypass routes are understood.

A mechanism that supports generic or persistent approval must demonstrate that those broader semantics cannot satisfy this authority gate.

## 6. Falsification Matrix

The investigation should actively attempt to defeat each candidate mechanism.

| Case                                                 | Required result                                                  |
| ---------------------------------------------------- | ---------------------------------------------------------------- |
| Human approves exact candidate A                     | A can be consumed once                                           |
| Human rejects A                                      | No authority exists                                              |
| Human dismisses/closes interaction                   | No authority exists                                              |
| Candidate content changes after presentation         | Original approval cannot authorize changed candidate             |
| Candidate B differs by one authority-bearing byte    | Approval of A cannot authorize B                                 |
| Same approval is submitted twice                     | Second consumption is rejected                                   |
| Model claims `"user approved"`                       | Rejected as authority                                            |
| Model reproduces candidate digest                    | Insufficient without trusted human action                        |
| Model invokes the underlying command/tool directly   | Cannot create human authority                                    |
| Programmatic command dispatch invokes the UI path    | Must not masquerade as human confirmation                        |
| Existing `allow` permission exists                   | Does not authorize candidate                                     |
| Existing `always` permission exists                  | Does not authorize candidate                                     |
| Automatic permission behavior is enabled             | Does not authorize candidate                                     |
| Different session attempts to consume candidate      | Rejected unless explicitly part of the proven binding            |
| Different agent attempts to consume candidate        | Rejected unless explicitly permitted by the proven design        |
| Interaction response is lost/ambiguous               | No authority is inferred                                         |
| Host/plugin restarts before approval                 | Pending-candidate behavior is explicit and safe                  |
| Host/plugin restarts after recorded approval         | Durable result still identifies exactly the authorized candidate |
| Already-consumed candidate is replayed after restart | Rejected                                                         |

Additional adversarial cases should be added whenever investigation exposes another plausible bypass.

## 7. Intent and Commit Scenarios

A mechanism should not pass M0 solely by supporting a convenient planning UI.

The same underlying authorization property must be demonstrated for two representative scenarios.

### Intent authorization

Present a candidate containing enough information for a human to understand the authority being granted, including at minimum:

* requested intent;
* exact repository scope;
* repository/worktree identity;
* bound baseline information relevant to approval.

The experiment does not need to settle the final production representation.

It only needs to establish that the exact candidate shown to the human is the exact candidate authorized.

### Commit authorization

Present a different candidate representing authority to commit an already reviewed target.

It should be capable of binding at least:

* the passing review identity/digest;
* the exact reviewed target or target digest;
* exact commit paths;
* relevant current Git baseline;
* human-readable commit intent/summary.

Changing the reviewed target after presentation must invalidate the authorization.

Intent approval must not substitute for commit approval.

## 8. Proof Method

Milestone 0 is an empirical host-boundary investigation.

For every candidate mechanism:

1. identify the OpenCode API and host behavior relied upon;
2. construct the smallest experiment that exercises the human interaction;
3. observe the exact host-supplied data available before, during, and after the interaction;
4. test the falsification matrix;
5. determine which properties are guaranteed by OpenCode and which are merely assumptions of the prototype;
6. document any bypass or ambiguity immediately;
7. stop pursuing the mechanism when a required property cannot be established.

Disposable repositories and disposable OpenCode sessions should be used where needed.

The purpose is not to make a polished UI.

The purpose is to establish the authority boundary.

## 9. Evidence Standard

A claim should be classified as one of:

### Proven

Observed end-to-end with a focused experiment, with enough evidence to reproduce the result.

### Host contract

Explicitly guaranteed by the supported OpenCode API or documented behavior relied upon by the design.

Host contracts that are safety-critical should still receive a focused runtime test where practical.

### Assumption

Believed true but not mechanically or contractually established.

A safety-critical assumption prevents M0 from passing.

### Rejected

Experimentation demonstrated that the mechanism cannot satisfy the required property without violating the milestone constraints.

The final M0 report should clearly distinguish these categories.

## 10. Outcomes

Milestone 0 has three legitimate outcomes.

### PASS

An OpenCode-native mechanism demonstrates:

* explicit human provenance;
* exact candidate binding;
* one-time consumption;
* replay resistance;
* fail-closed ambiguous behavior;
* independence from model claims and generic permission state;

without requiring infrastructure that materially changes the proposed small authority architecture.

A PASS permits architecture work on the Coding Authority Protocol to continue.

It does not by itself prove the rest of the protocol.

### HOST GAP

The required authority model appears sound, but the current supported OpenCode API does not expose enough trustworthy information or interaction semantics to implement it directly.

Examples might include:

* no trustworthy human-origin signal;
* no way to distinguish programmatic dispatch from user action;
* insufficient binding between displayed resource and returned action;
* unavoidable ambiguity caused by generic permission behavior.

A HOST GAP should trigger a decision about whether a small OpenCode API enhancement is reasonable.

It should not automatically trigger construction of an MCP server or separate authority daemon.

### FAIL

The required property cannot be achieved without trusting model/conversation claims, broad permission state, replayable inputs, or infrastructure comparable in complexity to the architecture `opencode-agents` is intended to avoid.

A FAIL requires architectural reconsideration before further implementation.

## 11. Stop Conditions

Do not broaden Milestone 0 to solve adjacent problems.

Specifically, stop before designing:

* the complete run schema;
* workflow phases;
* implementation/review transitions;
* Git receipt formats;
* validation policy;
* repair behavior;
* recovery protocols;
* agent prompts;
* installation/distribution architecture.

Minimal temporary state or code may be introduced only when needed to prove the authorization property.

If the proof starts requiring general workflow infrastructure, treat that as evidence against the candidate mechanism rather than justification for building the infrastructure.

## 12. Milestone Deliverable

The milestone should end with a short evidence report containing:

* OpenCode version/API surface tested;
* mechanisms investigated;
* experiments performed;
* falsification results;
* relied-upon host guarantees;
* unresolved assumptions;
* selected mechanism, if any;
* outcome: `PASS`, `HOST GAP`, or `FAIL`;
* architectural consequences.

If the outcome is `PASS`, the next architecture work should define the Coding Authority Protocol around the proven primitive.

If the outcome is `HOST GAP` or `FAIL`, do not proceed as though exact human authorization has been solved.
